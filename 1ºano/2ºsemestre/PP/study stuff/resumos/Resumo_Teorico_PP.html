01

Tipos Primitivos, Variáveis e Arrays

1.1 Tipos Primitivos

Java possui 8 tipos primitivos. Os tipos primitivos armazenam o valor diretamente na Stack de execução da JVM e não são considerados objetos:

byte (8 bits), short (16 bits), int (32 bits), long (64 bits), float (32 bits), double (64 bits), char (16 bits Unicode) e boolean (true/false).

Os valores por defeito dos tipos primitivos, quando declarados como atributos de instância de uma classe, são: 0 para numéricos inteiros, 0.0 para reais, '\u0000' para char e false para boolean. As variáveis locais declaradas no corpo dos métodos não possuem valores por defeito, obrigando o compilador a validar a sua inicialização obrigatória antes de qualquer utilização.

public class ExemploPrimitivos {
    // Variáveis de instância: inicializadas automaticamente com valores por defeito
    int numero;         // Valor por defeito: 0
    boolean ativo;      // Valor por defeito: false
    char letra;         // Valor por defeito: '\u0000'
    String referencia;  // Valor por defeito: null (tipo de referência)

    public void demonstrar() {
        // Variável local: não tem valor por defeito
        int x;
        // System.out.println(x); // ERRO de compilação: variável x pode não ter sido inicializada!
        
        x = 10; // Inicialização local obrigatória antes do uso
        System.out.println(x); // Compila com sucesso
    }
}

1.2 Constantes

As constantes em Java são declaradas recorrendo à palavra reservada final. Uma vez atribuído um valor à constante, este torna-se imutável e qualquer tentativa de reatribuição origina um erro em tempo de compilação. Por convenção de escrita, os identificadores de constantes são escritos integralmente em maiúsculas com underscores.

final double PI = 3.14159;
final int MAX_ELEMENTOS = 100;

1.3 Arrays

Os arrays em Java são estruturas de dados estáticas de dimensão fixa na memória que armazenam elementos do mesmo tipo de forma sequencial. O tamanho é definido obrigatoriamente na criação e não pode ser alterado posteriormente.

Os arrays de tipos primitivos são inicializados automaticamente com os valores padrão de cada tipo. Os arrays de referências de objetos são inicializados preenchendo todas as posições com a referência nula null.

int[] numeros = new int[5];         // Array de primitivos (tudo inicializado a 0)
String[] nomes = new String[3];     // Array de objetos (tudo inicializado a null)
int[] preDef = {1, 2, 3, 4, 5};    // Inicialização literal direta

Atenção: Para simular o redimensionamento de um array é necessário instanciar um novo array com a nova dimensão desejada e transferir manualmente os dados do array antigo para o novo bloco contíguo de memória Heap.

02

Classes e Objetos

2.1 Conceito de Classe

Uma classe atua como um molde ou especificação que define a estrutura de dados (atributos) e o comportamento operacional (métodos) que os objetos instanciados a partir dela vão partilhar.

public class Contentor {
    private String codigo;       // Atributo de instância (estado)
    private double capacidade;   // Atributo de instância (estado)

    public String getCodigo() {  // Método de instância (comportamento)
        return codigo;
    }
}

2.2 Criação de Objetos

Os objetos reais são criados através do operador new, que solicita à JVM a alocação de memória na Heap correspondente ao tamanho da classe e invoca o respetivo método construtor. A variável local que declara o tipo da classe armazena apenas um valor de referência contendo o endereço físico de memória da instância na Heap.

Contentor c = new Contentor();
// 'c' reside na Stack e armazena o endereço que aponta para o objeto na Heap

2.3 Variáveis de Instância vs Variáveis de Classe (static)

As variáveis de instância pertencem a cada objeto individualmente, existindo cópias separadas na memória Heap de cada objeto instanciado. As variáveis de classe, declaradas com o modificador static, pertencem à própria classe de forma global, existindo apenas uma única cópia alocada em memória partilhada por todas as instâncias.

public class Veiculo {
    private String matricula;            // Variável de instância
    private static int totalVeiculos = 0; // Variável de classe (partilhada)

    public Veiculo(String matricula) {
        this.matricula = matricula;
        totalVeiculos++;   // Modifica o estado partilhado global
    }

    public static int getTotalVeiculos() {  // Método estático
        return totalVeiculos;
    }
}

Regra: Métodos estáticos pertencem ao contexto da classe e não possuem contexto de instância. Logo, não podem aceder a atributos de instância não-estáticos nem utilizar as referências de controlo 'this' ou 'super'.

03

Construtores

3.1 Definição

Os construtores são blocos de código especiais encarregues de inicializar o estado de um objeto durante a instanciação com new. Apresentam as seguintes regras rígidas de sintaxe: devem possuir obrigatoriamente o mesmo nome exato da classe e não admitem qualquer tipo de retorno, nem mesmo a palavra-chave void.

public class Livro {
    private String titulo;

    // Construtor: mesmo nome da classe, sem tipo de retorno
    public Livro(String titulo) {
        this.titulo = titulo;
    }
    
    // public void Livro(String titulo) {} 
    // ^ ATENÇÃO: Isto não é um construtor, é um método comum que retorna void!
}

3.2 Construtor por Defeito

Se nenhuma declaração de construtor for especificada pelo programador na escrita da classe, o compilador gera em tempo de compilação um construtor por defeito sem parâmetros. Este construtor invoca a inicialização da superclasse com `super()` e define o valor padrão para todos os campos. Se o programador escrever qualquer construtor parametrizado, o construtor automático por defeito deixa de ser gerado.

public class ExemploDefeito {
    // 1. Sem qualquer construtor: o compilador gera automaticamente o construtor vazio.
    // public ExemploDefeito() { super(); }
}

class OutraClasse {
    private int valor;

    // Construtor parametrizado escrito manualmente
    public OutraClasse(int valor) {
        this.valor = valor;
    }
    
    // Como definimos o construtor acima, o construtor por defeito sem parâmetros deixa de existir!
    // OutraClasse o = new OutraClasse(); // ERRO de compilação!
    // OutraClasse o = new OutraClasse(10); // Correto
}

3.3 Encadeamento de Construtores

Podemos interligar múltiplos construtores dentro da mesma classe recorrendo ao método de chamada this(...) com argumentos, o que previne a repetição de lógica de inicialização de atributos. O aceso aos construtores da superclasse realiza-se através de super(...). Ambas as chamadas devem obrigatoriamente figurar como a primeira instrução no corpo do construtor e são mutuamente exclusivas.

public class AidBox {
    private String code;
    private String zone;

    public AidBox(String code) {
        this(code, "Desconhecida");    // Encaminha a inicialização
    }

    public AidBox(String code, String zone) {
        this.code = code;
        this.zone = zone;
    }
}
04

Encapsulamento e Modificadores de Acesso

4.1 Conceito de Encapsulamento

O encapsulamento visa a proteção da integridade dos dados internos de um objeto. O estado interno (atributos) deve ser blindado a acessos externos não validados declarando os campos como privados. O acesso ou mutação do estado realiza-se unicamente através de métodos públicos getters e setters que validam a consistência das operações.

public class ContaBancaria {
    private double saldo; // Privado: impossibilita acesso e modificação direta externa

    public double getSaldo() {
        return this.saldo;
    }

    public void depositar(double valor) {
        if (valor > 0) { // Validação do estado e proteção de regras de negócio
            this.saldo += valor;
        }
    }
}
// ContaBancaria conta = new ContaBancaria();
// conta.saldo = -500; // ERRO de compilação!
// conta.depositar(100); // Correto e seguro

4.2 Modificadores de Acesso

Java dispõe de quatro níveis de visibilidade controlada:

  • private: Acesso restrito estritamente a código definido dentro da própria classe.
  • protected: Acesso permitido no mesmo pacote de classes e a subclasses derivadas (mesmo localizadas em pacotes externos).
  • Sem modificador (package-private): Visibilidade restrita às classes contidas no mesmo pacote lógico.
  • public: Acesso livre a partir de qualquer classe em qualquer pacote da aplicação.
package pacoteA;

public class ClasseA {
    public int a = 1;       // Qualquer classe acede
    protected int b = 2;    // Mesmo pacote ou subclasses em outros pacotes
    int c = 3;              // Package-private (sem modificador): apenas neste pacote
    private int d = 4;      // Apenas dentro de ClasseA
}

package pacoteB;
import pacoteA.ClasseA;

public class ClasseB extends ClasseA {
    public void testarAcesso() {
        System.out.println(this.a); // Válido (public)
        System.out.println(this.b); // Válido (protected na subclasse)
        // System.out.println(this.c); // ERRO: c é package-private e ClasseB está noutro pacote
        // System.out.println(this.d); // ERRO: d é privado da ClasseA
    }
}

4.3 Getters e Setters com Validação

public class Container {
    private double capacidade;
    private double pesoAtual;

    public double getCapacidade() {
        return capacidade;
    }

    public void setPesoAtual(double peso) {
        // Validação defensiva do estado
        if (peso < 0 || peso > capacidade) {
            throw new IllegalArgumentException("Peso invalido.");
        }
        this.pesoAtual = peso;
    }
}
05

Enumerações (Enum)

As enumerações representam um tipo especial de classe Java concebida para gerir um conjunto fixo e fechado de constantes semânticas. Cada valor do enum constitui uma instância do tipo singleton. A comparação lógica de enums realiza-se de forma direta e segura através do operador relacional ==.

Os enums em Java suportam a declaração de atributos, construtores (obrigatoriamente privados) e métodos de instância ou estáticos.

public enum ItemType {
    PERISHABLE_FOOD("Alimentos Pereciveis"),
    NON_PERISHABLE_FOOD("Alimentos Nao Pereciveis"),
    CLOTHING("Vestuario"),
    MEDICINE("Medicamentos");

    private String descricao;

    ItemType(String descricao) { // Construtor implicitamente privado
        this.descricao = descricao;
    }

    public String getDescricao() {
        return descricao;
    }
}

Vantagens: Garante segurança de tipo (Type Safety) impedindo valores arbitrários inválidos em tempo de compilação, promove legibilidade e integração direta em blocos 'switch'.

06

Métodos e Sobrecarga

6.1 Definição de Métodos

Um método define o comportamento operacional da classe. É estruturado através da sua assinatura de método, que consiste na combinação do nome do método e da lista ordenada de parâmetros (tipos e quantidade). O tipo de retorno não faz parte da assinatura do método.

public class Calculadora {
    // Assinatura: somar(int, int)
    public int somar(int a, int b) { 
        return a + b; 
    }
    
    // public double somar(int x, int y) { return x + y; }
    // ^ ERRO de compilação: mesma assinatura somar(int, int).
    // O tipo de retorno e nomes dos parâmetros não diferenciam a assinatura!
}

6.2 Sobrecarga de Métodos (Overloading)

A sobrecarga consiste na declaração de múltiplos métodos com o mesmo nome na mesma classe, desde que apresentem assinaturas distintas (diferente quantidade ou tipo de parâmetros). A seleção do método a executar realiza-se estritamente em tempo de compilação.

public int somar(int a, int b) { return a + b; }
public double somar(double a, double b) { return a + b; }
public int somar(int a, int b, int c) { return a + b + c; }
07

Passagem de Argumentos

Em Java, toda a passagem de argumentos para métodos é efetuada estritamente por valor. Não existe passagem por referência nativa no Java.

Para tipos primitivos, copia-se o valor direto na pilha local do método. Modificações na variável local do método não têm impacto na variável original do método chamador.

Para tipos de referência (objetos), é copiado o endereço físico de memória da referência. Como a variável local e a variável original possuem cópias do mesmo endereço de memória, ambas apontam para o mesmo objeto na Heap. Modificações no estado interno do objeto (atributos) são visíveis globalmente. Contudo, efetuar a reatribuição da referência local (ex: param = new Objeto()) altera apenas o endereço na Stack local, deixando a referência original intocada.

public static void alterarEstado(int[] arr) {
    arr[0] = 999;   // Afeta o array partilhado na Heap
}

public static void reatribuir(int[] arr) {
    arr = new int[]{1, 2, 3};   // Altera apenas o ponteiro da cópia na Stack local
}
08

Herança

8.1 Conceito

A herança apoia a reutilização de comportamento através da definição de hierarquias onde uma subclasse (especialização) estende membros públicos e protegidos de uma superclasse (generalização). Java suporta apenas a herança simples de classes recorrendo à palavra extends.

// Superclasse
public class Animal {
    protected String nome;
    
    public void comer() {
        System.out.println(nome + " esta a comer.");
    }
}

// Subclasse
public class Cao extends Animal {
    public void ladrar() {
        System.out.println("Woof!");
    }
}
// Uso:
// Cao c = new Cao();
// c.nome = "Bobby"; // Acede a atributo protected herdado
// c.comer();       // Executa método herdado da Superclasse
// c.ladrar();      // Executa método específico da Subclasse

8.2 A Palavra Reservada super

No construtor, super(...) invoca a lógica de inicialização do pai e tem de ser invocado obrigatoriamente na primeira linha do bloco. No corpo dos métodos, a instrução super.metodo() executa a versão original do método da superclasse que foi sobreposto.

public class Veiculo {
    private String matricula;

    public Veiculo(String matricula) {
        this.matricula = matricula;
    }
}

public class Camiao extends Veiculo {
    private double cargaMax;

    public Camiao(String matricula, double cargaMax) {
        super(matricula); // Invocação do construtor pai
        this.cargaMax = cargaMax;
    }
}

8.3 Sobreposição de Métodos (Overriding)

A sobreposição ocorre quando um método da superclasse é redefinido na subclasse contendo a mesma assinatura e tipo de retorno compatível (ou covariante). O compilador valida a redefinição sob a anotação @Override. A seleção do método a executar é dinâmica e decidida em tempo de execução pela JVM com base na classe da instância real na Heap.

public class Animal {
    public void emitirSom() {
        System.out.println("Som generico de animal");
    }
}

public class Gato extends Animal {
    @Override // O compilador valida se a assinatura coincide exatamente
    public void emitirSom() {
        System.out.println("Miau!");
    }
}
// Polimorfismo:
// Animal a = new Gato();
// a.emitirSom(); // Imprime "Miau!" (determinado dinamicamente no runtime)
09

Casting (Conversão de Tipos)

9.1 Upcasting

Conversão ascendente de uma referência de subclasse para superclasse. É uma operação automática (implícita) e perfeitamente segura. Implica a perda de visibilidade imediata de métodos exclusivos da subclasse, mantendo as invocações polimórficas.

Vehicle v = new RefrigeratedVehicleImpl("V-001", ...); // Upcasting implícito
v.getCode(); // Métodos comuns do contrato principal são válidos

9.2 Downcasting

Conversão descendente de uma referência genérica da superclasse para o tipo mais específico da subclasse. Requer um operador de coerção explícito e comporta perigos. Caso o objeto real na Heap não pertença à subclasse de destino, a JVM lança a exceção ClassCastException. É boa prática salvaguardar com instanceof.

if (v instanceof RefrigeratedVehicle) {
    RefrigeratedVehicle rv = (RefrigeratedVehicle) v; // Downcasting explícito seguro
    double km = rv.getMaxKilometers();
}
10

Classes Abstratas

Uma classe abstrata (delcarada com a palavra-chave abstract) destina-se a servir de base conceitual para subclasses, não podendo ser instanciada diretamente com new. Pode alojar métodos concretos com comportamento partilhado e métodos abstratos sem corpo que as subclasses concretas são obrigadas a sobrepor.

public abstract class Transporte {
    private String id;

    public Transporte(String id) {
        this.id = id;
    }

    public String getId() { return id; }
    public abstract double calcularCusto(double km); // Método abstrato (contrato)
}

O modificador final impede a extensão de classes, redefinição de métodos ou reatribuição de variáveis.

11

Interfaces

Uma interface serve para estabelecer um contrato puro de comportamento que qualquer classe pode assumir através de implements. Suporta a herança múltipla de tipo (uma classe implementa variadas interfaces). Todos os atributos declarados em interfaces são implicitamente constantes public static final.

public interface Vehicle {
    String getCode();
    ItemType getSupplyType();
}

A partir do Java 8, as interfaces toleram métodos concretos declarados como default (implementação padrão opcional) ou métodos static. O Java 9 adicionou suporte a métodos private para fins de reutilização de lógica interna.

12

Classes Abstratas vs Interfaces — Comparação Direta

Classes Abstratas: Estão integradas em hierarquias rígidas de herança simples. Têm a faculdade de reter e gerir variáveis de estado de instância mutáveis. Permitem a declaração de construtores de inicialização. Indicadas para relações "É UM".

Interfaces: Propiciam maior flexibilidade sob herança múltipla de tipo. São vedadas de armazenar variáveis de estado de instância, aceitando apenas constantes globais. Desprovidas de construtores. Indicadas para relações de comportamento do tipo "CONSEGUE FAZER".

// Classe Abstrata (Relação "É UM")
public abstract class Veiculo {
    private String matricula; // Pode ter atributos de instância mutáveis

    public Veiculo(String matricula) { // Pode declarar construtores
        this.matricula = matricula;
    }
    
    public abstract void mover();
}

// Interface (Relação "CONSEGUE FAZER")
public interface Eletrico {
    // Atributos são implicitamente public static final (constantes)
    int VOLTAGEM_PADRAO = 230; 
    
    void carregar(); // Métodos abstratos por defeito
}

// Classe concreta: herança simples (extends) + implementação múltipla (implements)
public class Tesla extends Veiculo implements Eletrico {
    public Tesla(String matricula) {
        super(matricula);
    }

    @Override
    public void mover() { System.out.println("A acelerar eletricamente..."); }

    @Override
    public void carregar() { System.out.println("Bateria a carregar..."); }
}
13

Polimorfismo

13.1 Polimorfismo de Sobreposição (Dynamic Binding)

Ocorre em tempo de execução. O tipo formal da referência do objeto decide que métodos são permitidos ao compilar, mas no runtime a JVM executa a implementação da classe concreta baseada na instância real da Heap. Permite o tratamento uniforme de objetos de diferentes tipos sob uma mesma referência ancestral comum.

public class Funcionario {
    public double getSalario() { return 1000.0; }
}

public class Diretor extends Funcionario {
    @Override
    public double getSalario() { return 3000.0; }
}

// Demonstração:
Funcionario f1 = new Funcionario(); // Formal: Funcionario, Real: Funcionario
Funcionario f2 = new Diretor();     // Formal: Funcionario, Real: Diretor (Upcasting)

System.out.println(f1.getSalario()); // Imprime 1000.0
System.out.println(f2.getSalario()); // Imprime 3000.0 (Dynamic Binding na JVM)

13.2 Polimorfismo de Sobrecarga (Static Binding)

Ocorre em tempo de compilação. A JVM seleciona o método específico a invocar com base estrita no tipo dos argumentos declarados na chamada.

public class Impressora {
    public void imprimir(String s) { System.out.println("Texto: " + s); }
    public void imprimir(int i)    { System.out.println("Inteiro: " + i); }
}

Impressora imp = new Impressora();
imp.imprimir("Ola"); // Compilador resolve para imprimir(String)
imp.imprimir(100);   // Compilador resolve para imprimir(int)
14

Identidade vs Igualdade de Objetos

14.1 O Operador ==

Compara a igualdade binária nos primitivos e a igualdade referencial nos objetos (verifica se ambas as variáveis apontam para a mesma morada física de memória Heap).

String s1 = new String("exemplo");
String s2 = new String("exemplo");
String s3 = s1;

System.out.println(s1 == s2); // false (são objetos diferentes na Heap)
System.out.println(s1 == s3); // true (apontam para o mesmo objeto na Heap)

14.2 O Método equals()

Destina-se a definir a igualdade semântica ou lógica com base em campos de dados. A implementação original na classe Object limita-se a usar ==, obrigando à sua sobreposição nas classes de negócio.

String s1 = new String("exemplo");
String s2 = new String("exemplo");

System.out.println(s1.equals(s2)); // true (compara o conteúdo semântico)

14.3 A Estrutura de equals Padrão

@Override
public boolean equals(Object obj) {
    if (this == obj) return true;                      // 1. Identidade
    if (obj == null) return false;                     // 2. Nulo
    if (!(obj instanceof Vehicle)) return false;       // 3. Compatibilidade de Tipo
    Vehicle other = (Vehicle) obj;                     // 4. Cast seguro
    return this.code.equals(other.getCode());          // 5. Lógica de campos
}

14.4 instanceof vs getClass()

O operador instanceof aceita correspondências em subclasses descendentes da hierarquia e implementações de interfaces (visão polimórfica flexível). A instrução getClass() == obj.getClass() valida estritamente a mesma classe exata, excluindo classes derivadas (garantia rígida de simetria do contrato equals).

class Animal {}
class Cao extends Animal {}

Animal a = new Cao();

// 1. instanceof (polimórfico, inclui subclasses)
System.out.println(a instanceof Animal); // true (a é subclasse de Animal)
System.out.println(a instanceof Cao);    // true

// 2. getClass() (exato, exclui subclasses)
System.out.println(a.getClass() == Animal.class); // false (tipo real é Cao)
System.out.println(a.getClass() == Cao.class);    // true
15

Exceções

15.1 Hierarquia

Toda a estrutura deriva de Throwable, ramificando em Error (situações catastróficas da máquina virtual irrecuperáveis) e Exception (anomalias de fluxo lógico controláveis).

15.2 Checked vs Unchecked

As exceções verificadas (checked) são subclasses de Exception (com exceção das descendentes de RuntimeException). O compilador obriga a tratá-las explicitamente com try-catch ou a delegar o aviso na assinatura do método com a cláusula throws.

As exceções não verificadas (unchecked) herdam de RuntimeException. O compilador dispensa a verificação obrigatória, indicando habitualmente falhas ou inconsistências de desenvolvimento de código (ex: NullPointerException).

// Exceção Unchecked (Runtime)
public class SaldoInsuficienteException extends RuntimeException {
    public SaldoInsuficienteException(String m) { super(m); }
}

// Exceção Checked (exige tratamento ou throws obrigatório)
public class ConexaoFalhadaException extends Exception {
    public ConexaoFalhadaException(String m) { super(m); }
}

public class ServicoBancario {
    // 1. Checked exception: TEM de declarar throws na assinatura do método
    public void conectarServidor() throws ConexaoFalhadaException {
        throw new ConexaoFalhadaException("Timeout de conexao.");
    }

    // 2. Unchecked exception: NÃO necessita declarar throws na assinatura
    public void levantar(double valor) {
        if (valor > 1000) {

Composição vs Herança

A herança constitui uma ligação forte e estática baseada em relações "É UM", herdando a totalidade de membros da superclasse de forma direta. A composição propõe uma dependência fraca e dinâmica onde uma classe integra instâncias de outros objetos na sua declaração de atributos, estabelecendo relações do tipo "TEM UM".

A composição é comummente preferida à herança para reduzir o acoplamento sistémico entre classes, flexibilizar a substituição dinâmica de comportamentos em tempo de execução e contornar problemas de fragilidade inerentes à herança (onde mudanças na classe base afetam inesperadamente o funcionamento das subclasses).

// Herança (Relação "É UM")
public class Carro extends Veiculo {
    // Herda todos os atributos e comportamentos de Veiculo
}

// Composição (Relação "TEM UM")
public class Motor {
    public void arrancar() { System.out.println("Motor ligado."); }
}

public class CarroComposto {
    private Motor motor; // O Carro TEM UM Motor

    public CarroComposto() {
        this.motor = new Motor();
    }

    public void ligar() {
        this.motor.arrancar(); // Delegação do trabalho ao motor composto
    }
}

Membros Estáticos (static)

Atributos e métodos estáticos pertencem conceptualmente ao escopo da classe, desvinculados de qualquer instância individual. Existe uma única alocação física do campo na memória JVM, que é partilhada por todas as instâncias da classe. Métodos estáticos podem ser chamados diretamente a partir do identificador da classe, estando impedidos de referenciar this ou interagir com campos de instância não-estáticos.

public class Contador {
    public static int contagemGlobal = 0; // Atributo estático (partilhado por todos)
    public int idInstancia = 0;           // Atributo de instância (único de cada objeto)

    public static void incrementar() {
        contagemGlobal++;
        // this.idInstancia++; // ERRO de compilação! Contexto estático não tem 'this'.
        // idInstancia = 1;    // ERRO de compilação! Não pode aceder a variáveis não-estáticas.
    }
}

// Contador.incrementar();

A Palavra-Chave final

O modificador final confere propriedades de imutabilidade consoante o seu contexto de aplicação:

  • Em variáveis: Estabelece constantes, impedindo a reatribuição de valores a campos primitivos ou reatribuição de moradas de memória a referências.
  • Em métodos: Proíbe expressamente a sua sobreposição pelas subclasses na hierarquia.
  • Em classes: Trunca a herança, impedindo a criação de quaisquer subclasses a partir da classe final.
// 1. Classe final: não permite herança
public final class CalculadorMatematico {
    
    // 2. Variável/Atributo final: imutável
    public final double PI = 3.14159;

    // 3. Método final: impede overriding (sobreposição) nas subclasses
    public final void mostrarFormula() {
        System.out.println("Formula imutavel.");
    }
}
// class SuperCalculador extends CalculadorMatematico {} // ERRO de compilação!

20.2 Gestão de Arrays Estáticos (Adicionar e Remover)

private Elemento[] elementos;
private int count;

public void add(Elemento e) throws MinhaExcecao {
    if (e == null) throw new MinhaExcecao("Nulo.");
    if (count >= elementos.length) throw new MinhaExcecao("Cheio.");
    for (int i = 0; i < count; i++) {
        if (elementos[i].equals(e)) throw new MinhaExcecao("Duplicado.");
    }
    elementos[count] = e;
    count++;
}

public Elemento remove(Elemento e) throws MinhaExcecao {
    for (int i = 0; i < count; i++) {
        if (elementos[i].equals(e)) {
            Elemento removed = elementos[i];
            for (int j = i; j < count - 1; j++) {
                elementos[j] = elementos[j + 1];
            }
            elementos[count - 1] = null;
            count--;
            return removed;
        }
    }
    throw new MinhaExcecao("Nao encontrado.");
}

public Elemento[] getElementos() {

    }
    return result;
}

Pergunta 1: Classes Abstratas vs Interfaces (1.5 valores)

Questão: Explique detalhadamente as diferenças entre classes abstratas e interfaces em Java. Em que situações é mais adequado optar por uma classe abstrata e em que situações é preferível uma interface? Justifique a sua resposta e ilustre cada caso com um exemplo prático que evidencie as características distintivas de cada mecanismo.

Resposta Padrão:

  • Diferenças Principais:
    • Estado: Classes abstratas podem conter atributos de instância mutáveis (estado privado/protegido do objeto). Interfaces (até ao Java 8) apenas aceitam constantes públicas, estáticas e finais (public static final).
    • Construtores: Classes abstratas podem definir construtores (para inicializar atributos partilhados). Interfaces não os admitem.
    • Herança: Java limita a herança a uma única classe (herança simples de classes). Em contrapartida, permite herança múltipla de tipo com múltiplas interfaces.
    • Métodos: Métodos em classes abstratas são concretos por omissão (devem usar abstract se não tiverem corpo). Em interfaces, são abstratos por defeito (Java 8 adicionou métodos default e static, e Java 9 métodos private).
  • Critérios de Escolha:
    • Classe Abstrata (Relação "É UM"): Indicada se as subclasses fizerem parte de uma árvore hierárquica estrita e precisarem de partilhar código comum estrutural (atributos de instância e lógica de inicialização no construtor).
    • Interface (Relação "CONSEGUE FAZER"): Preferível para estabelecer contratos de comportamento transversais a classes em diferentes ramificações da hierarquia (ex: ser recarregável ou imprimível).
// CLASSE ABSTRATA: Define estado comum e construtor
public abstract class Veiculo {
    private String matricula; // Atributo de instância mutável

    public Veiculo(String matricula) {
        this.matricula = matricula;
    }
    public String getMatricula() { return matricula; }
    public abstract void mover(); // Comportamento abstrato obrigatório
}

// INTERFACE: Estabelece capacidade de carregamento
public interface Carregavel {
    void carregar(); // Método abstrato por omissão
}

// Implementação que herda do pai e assume o contrato da interface
public class CarroTesla extends Veiculo implements Carregavel {
    public CarroTesla(String matricula) {
        super(matricula);
    }
    @Override
    public void mover() { System.out.println("A acelerar silenciosamente..."); }
    @Override
    public void carregar() { System.out.println("Tesla ligado ao Supercharger."); }
}

Pergunta 2: Passagem de Argumentos em Métodos (1.5 valores)

Questão: Descreva detalhadamente o modo como Java realiza a passagem de argumentos para os métodos, distinguindo o comportamento aplicado a tipos primitivos do comportamento aplicado a referências de objetos. Esclareça os equívocos frequentes associados a este mecanismo e fundamente a sua explicação com exemplos concretos que demonstrem os efeitos sobre os valores e os estados dos objetos.

Resposta Padrão:

  • Regra Geral: Toda a passagem de argumentos em Java é efetuada estritamente por valor (cópia do conteúdo da variável). Não existe passagem por referência nativa.
  • Tipos Primitivos: O valor copiado é o próprio dado binário. Como a variável local é uma cópia na pilha local do método, alterações efetuadas sobre ela não afetam a variável de origem.
  • Referências de Objetos: O "valor" da variável de referência é o endereço físico de memória na Heap. Ao passar um objeto, copia-se esse endereço de memória. Portanto, ambas as variáveis (do chamador e local do método) apontam para a mesma instância física na Heap.
    • Modificar atributos: Modificações nos atributos do objeto (ex: obj.setSaldo(...)) são visíveis globalmente porque o objeto real na Heap é partilhado.
    • Reatribuição (O Equívoco Comum): Reatribuir a referência em si (ex: obj = new MinhaClasse()) apenas altera a cópia local do endereço na Stack do método, deixando a referência original do chamador intacta.
public class TestePassagem {
    public static void alterarPrimitivo(int x) {
        x = 99; // Altera apenas o valor local na Stack
    }
    
    public static void modificarObjeto(Conta conta) {
        conta.saldo = 500.0; // Altera o objeto partilhado na Heap
    }
    
    public static void tentarReatribuir(Conta conta) {
        conta = new Conta(); // Altera apenas a variável de referência local
        conta.saldo = 2000.0;
    }
    
    public static void main(String[] args) {
        int valor = 10;
        alterarPrimitivo(valor);
        System.out.println(valor); // Imprime 10 (primitivo inalterado)

        Conta c = new Conta();
        c.saldo = 100.0;
        modificarObjeto(c);
        System.out.println(c.saldo); // Imprime 500.0 (objeto modificado na Heap)

        tentarReatribuir(c);
        System.out.println(c.saldo); // Imprime 500.0 (a reatribuição local falhou)
    }
}
class Conta { double saldo; }

Resposta Padrão:

        // Downcasting explícito seguro salvaguardado com instanceof

            Aviao a2 = (Aviao) v;
            a2.voar(); // Executa corretamente

Pergunta 4: Identidade vs Igualdade e toString (1.5 valores)

Questão: Distinga os conceitos de identidade e de igualdade de objetos em Java, esclarecendo a diferença entre o operador `==` e o método `equals()`. Explique igualmente o papel do método `toString()`. Forneça um exemplo prático que demonstre a redefinição correta dos métodos `equals()` e `toString()` numa classe.

Resposta Padrão:

  • Identidade (Operador ==): Compara se duas referências contêm o mesmo endereço de memória na Stack, ou seja, se apontam para a mesma instância física na Heap.
  • Igualdade (Método equals()): Compara se os objetos são semanticamente ou logicamente equivalentes com base no seu conteúdo (atributos). A implementação padrão em Object limita-se a usar ==, pelo que deve ser sobreposta pelas classes de negócio.
  • Método toString(): Devolve uma String legível representativa do estado do objeto. A versão por defeito herdada de Object apenas devolve NomeClasse@HashCode.
public class Livro {
    private String isbn;
    private String titulo;

    public Livro(String isbn, String titulo) {
        this.isbn = isbn;
        this.titulo = titulo;
    }

    @Override
    public boolean equals(Object obj) {
        if (this == obj) return true; // Identidade
        if (obj == null) return false; // Nulo
        if (this.getClass() != obj.getClass()) return false; // Compatibilidade exata
        Livro other = (Livro) obj; // Cast seguro
        
        if (this.isbn == null) {
            return other.isbn == null;
        }
        return this.isbn.equals(other.isbn); // Igualdade baseada no ISBN
    }

    @Override
    public String toString() {
        return "Livro [ISBN=" + isbn + ", Titulo=" + titulo + "]";
    }
}

class Email extends Mensagem {

    public void enviar() { System.out.println("Email enviado via SMTP."); }

  • Herança ("É UM"): Vinculação estática rígida. A subclasse expõe e herda toda a API del pai diretamente.
  • Composição ("TEM UM"): Vinculação flexível onde um objeto guarda a referência de outros objetos para delegar comportamentos.
  • Preferência: A composição reduz o acoplamento, evita violações da API e contorna os riscos de quebra de subclasses decorrentes de modificações na classe pai (fragilidade da superclasse).
class Motor {
    public void ligar() { System.out.println("Motor ligado."); }
}

public class Carro {
    private Motor motor = new Motor(); // Composição

    public void conduzir() {
        motor.ligar(); // Delegação
        System.out.println("A conduzir...");
    }
}

Pergunta 1: Arrays de Objetos em Java (1.5 valores)

Questão: Explique o conceito de arrays de objetos em Java, distinguindo entre a criação do array e a criação dos objetos que o compõem. Descreva os cuidados necessários ao manipular arrays de objetos, nomeadamente a verificação de posições nulas. Explique também como se pode redimensionar um array e por que razão os arrays em Java têm tamanho fixo. Ilustre com um exemplo prático.

Resposta Padrão:

  • Criação vs Instanciação: Ao declarar e instanciar um array de objetos (ex: Aluno[] al = new Aluno[5];), a JVM aloca espaço contíguo para 5 referências, que são inicializadas a null. Os objetos em si devem ser instanciados de forma individual e posterior.
  • Tamanho Fixo: Os arrays têm tamanho fixo para otimizar os acessos e leituras de memória (alocação de bloco contíguo na Heap). Para redimensionar, é obrigatório instanciar um novo array maior e transferir manualmente os dados.
public class TesteArrays {
    public static void main(String[] args) {
        String[] lista = new String[2]; // Criado o array com referências a null
        
        // System.out.println(lista[0].toUpperCase()); // Lançaria NullPointerException!
        
        lista[0] = new String("Ola"); // Instanciação manual
        
        // Redimensionamento manual
        String[] temp = new String[4];
        System.arraycopy(lista, 0, temp, 0, lista.length);
        lista = temp;
    }
}

Pergunta 2: instanceof vs getClass() (1.5 valores)

Questão: Compare detalhadamente a utilização de `instanceof` com a utilização de `getClass()` para verificação de tipos em Java. Discuta as diferenças de comportamento na presença de herança e interfaces, explique em que contextos cada abordagem é mais adequada e fundamente com exemplos concretos que evidenciem as diferenças.

Resposta Padrão:

  • instanceof: Operador polimórfico. Devolve true se o objeto for compatível com o tipo especificado, incluindo subclasses ou implementações de interfaces.
  • getClass(): Comparação de tipo exato. Devolve true apenas se os objetos forem instâncias da mesma classe exata, desconsiderando heranças.
  • Aplicações: instanceof deve ser usado em filtragens polimórficas. getClass() deve ser usado na implementação do método equals() quando se pretende evitar incompatibilidades de comparação simétrica em hierarquias de herança.
class Animal {}
class Cao extends Animal {}

public class TesteComparacao {
    public static void main(String[] args) {
        Animal a = new Cao();
        System.out.println(a instanceof Animal); // true
        System.out.println(a.getClass() == Animal.class); // false (tipo real é Cao)
    }
}

Pergunta 3: Membros Estáticos — static (1.5 valores)

Questão: Explique o conceito de membros estáticos (`static`) em Java, distinguindo entre atributos estáticos e métodos estáticos. Descreva como os membros estáticos se diferenciam dos membros de instância no que diz respeito ao ciclo de vida, ao acesso e à partilha de informação entre objetos. Ilustre com um exemplo prático que demonstre um caso de uso adequado para um atributo estático.

Resposta Padrão:

  • Conceito: Membros marcados com static pertencem à própria classe e são alocados em memória global uma única vez (partilhados por todas as instâncias).
  • Ciclo de Vida: Inicia com o carregamento da classe na JVM e termina com o encerramento do programa (independente de objetos criados com new).
  • Métodos Estáticos: Apenas acedem a dados estáticos. Não possuem contexto de instância (não admitem this nem acedem a atributos normais).
public class Veiculo {
    private static int totalVeiculos = 0; // Partilhado por todas as instâncias
    
    public Veiculo() {
        totalVeiculos++;
    }

    public static int getTotalVeiculos() {
        return totalVeiculos; // Acesso direto sem instanciar objetos
    }
}
