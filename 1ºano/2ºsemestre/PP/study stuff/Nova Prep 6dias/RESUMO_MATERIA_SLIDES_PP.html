APP01: Paradigma Orientado a Objetos e Encapsulamento

💡 Explicação Aprofundada da Matéria dos Slides:

Em Programação Orientada a Objetos (POO), o software é estruturado através de entidades autónomas designadas Objetos, que combinam estado (atributos) e comportamento (métodos).

  • Classe: Modelo abstrato que estabelece a estrutura e o comportamento de um novo tipo.
  • Objeto / Instância: Entidade concreta alocada na memória Heap através do operador new.

Os 4 Pilares da POO: Abstração, Encapsulamento, Herança e Polimorfismo.

Pergunta de Exame Encapsulamento e Modificadores de Acesso (1,5 valores)

Explique detalhadamente o conceito de Encapsulamento em Programação Orientada a Objetos. Descreva os 4 modificadores de acesso do Java (private, package-private / default, protected, public) por ordem crescente de permissividade. Justifique por que razão o acesso direto (public) aos atributos é uma má prática de programação e apresente um exemplo prático de getters e setters com validação defensiva.

📋 Resposta Modelo (1,5v): "Encapsulamento e Modificadores de Acesso"

  1. Conceito & Encapsulamento: O Encapsulamento oculta a estrutura interna de dados de uma classe, controlando a sua alteração exclusivamente por métodos públicos. Protege a integridade do estado e reduz o acoplamento.
  2. 4 Modificadores por Ordem Crescente de Permissividade:
    • private: Visível exclusivamente dentro da própria classe.
    • default (package-private): Visível apenas para classes do mesmo pacote Java.
    • protected: Visível para classes do mesmo pacote e para subclasses (mesmo noutros pacotes).
    • public: Acessível universalmente por qualquer classe em qualquer pacote.
  3. Má Prática de Atributos Public & Validação Defensiva: Declarar atributos como `public` permite que código externo injete dados inválidos (ex: capacidade negativa) sem qualquer validação, violando as regras de negócio. Soluciona-se com atributos `private` e mutadores públicos contendo validações que lançam exceções perante valores inválidos.

💻 Excerto de Código Ilustrativo:

public class AidBoxImpl {
    private String code;      // private: apenas visivel na propria classe
    private double capacity;  // atributo encapsulado

    public AidBoxImpl(String code, double capacity) {
        this.code = code;
        setCapacity(capacity); // Validação defensiva no construtor
    }

    public void setCapacity(double capacity) {
        if (capacity <= 0) {
            throw new IllegalArgumentException("Capacidade deve ser estritamente positiva.");
        }
        this.capacity = capacity;
    }

    public double getCapacity() { return this.capacity; }
}

APP02: Tipos de Dados, Memória JVM (Stack vs Heap) & Passagem de Argumentos

💡 Explicação Aprofundada da Matéria dos Slides:

A JVM divide a memória operacional em duas áreas essenciais:

  • Stack (Pilha de Execução): Organizada por Thread em quadros de métodos. Armazena variáveis locais, literais primitivos e ponteiros de referência para a Heap. Possui desalocação automática e instantânea ao sair do escopo do método.
  • Heap (Memória Dinâmica): Área global onde residem todos os objetos concretos e arrays criados via new. Gerida automaticamente pelo Garbage Collector (GC).

Atributos de Instância (Heap) vs Variáveis Locais (Stack)

AspetoAtributos de Instância (Heap)Variáveis Locais (Stack)
LocalizaçãoNo corpo da classe (fora de métodos).No corpo de métodos ou blocos.
Inicialização**AUTOMÁTICA pela JVM** (`0`, `0.0`, `false`, `null`).**SEM INICIALIZAÇÃO AUTOMÁTICA**.
Impacto de LeituraDevolve o valor padrão com segurança.**Erro de Compilação** ao ler sem atribuir valor.

Exame Época Normal 2025/2026 Passagem de Argumentos em Java (1,5 valores)

Descreva detalhadamente o modo como Java realiza a passagem de argumentos para os métodos, distinguindo o comportamento aplicado a tipos primitivos do comportamento aplicado a referências de objetos. Esclareça os equívocos frequentes associados a este mecanismo e fundamente a sua explicação com exemplos concretos que demonstrem os efeitos sobre os valores e os estados dos objetos.

📋 Resposta Modelo (1,5v): "Passagem de Argumentos (Primitivos vs Referências)"

  1. Mecanismo Pass-by-Value: Em Java, a passagem de argumentos é exclusivamente efetuada por valor (*pass-by-value*). Uma cópia do argumento é colocada na pilha (Stack) do método invocado.
  2. Tipos Primitivos vs Referências de Objetos:
    • Primitivos: É passada uma cópia do valor literal. Qualquer alteração ao parâmetro dentro do método afeta apenas a variável local da Stack, não alterando a variável original do chamador.
    • Referencias de Objetos: É passada uma cópia do **endereço de memória (ponteiro)** que aponta para o objeto na Heap. Como a cópia aponta para o mesmo objeto na Heap, invocar métodos mutadores (`setCapacity()`) altera o estado real do objeto visível fora do método.
  3. Equívoco Frequente da Reatribuição: Reatribuir o parâmetro de referência (`box = new ...`) faz com que a cópia local passe a apontar para outro objeto na Heap. No entanto, a variável de referência original do chamador permanece inalterada apontando para o objeto inicial.

💻 Excerto de Código Ilustrativo:

public class TestePassagem {
    public static void alterarPrimitivo(int x) {
        x = 999; // Altera APENAS a copia local na Stack. O 'a' original continua 10.
    }

    public static void alterarEstadoObjeto(AidBoxImpl box) {
        box.setCapacity(500.0); // Modifica a instancia REAL na Heap! Visivel fora.
    }

    public static void reatribuirReferencia(AidBoxImpl box) {
        box = new AidBoxImpl("NOVA", 100); // So altera a copia local do ponteiro!
    }

    public static void main(String[] args) {
        int a = 10;
        alterarPrimitivo(a); // a continua 10

        AidBoxImpl b = new AidBoxImpl("B-01", 50.0);
        alterarEstadoObjeto(b); // b.getCapacity() passa a 500.0
        reatribuirReferencia(b); // b continua a apontar para "B-01"!
    }
}

Pergunta de Exame Gestão de Memória JVM & Garbage Collector (1,5 valores)

Explique a Gestão de Memória na JVM (Java Virtual Machine), distinguindo a memória Stack da memória Heap. Descreva o ciclo de vida dos objetos, o conceito de elegibilidade (inalcançabilidade) para o Garbage Collector (GC) e as razões que levaram à descontinuação (deprecation) do método finalize() da classe Object.

📋 Resposta Modelo (1,5v): "Memória JVM, GC e Deprecation do finalize()"

  1. Stack vs Heap: A Stack guarda variáveis locais e referências com desalocação automática ao sair do método. A Heap guarda objetos e arrays instanciados com `new`.
  2. Elegibilidade para GC (Inalcançabilidade): Um objeto torna-se elegível para a recolha de lixo (*Garbage Collection*) quando fica **inalcançável**, ou seja, deixa de possuir qualquer referência ativa a apontar para ele a partir da Stack.
  3. Descontinuação do método `finalize()`: O método `finalize()` foi descontinuado (*deprecated*) porque a sua execução pelo GC é imprevisível, incerta e não garantida em tempo útil. Deve ser substituído por `try-with-resources` e a interface `AutoCloseable`.

💻 Excerto de Código Ilustrativo:

public class MemoriaGC {
    public void demonstrarElegibilidade() {
        AidBoxImpl b1 = new AidBoxImpl("BOX1", 10); // Instancia 1 na Heap
        AidBoxImpl b2 = new AidBoxImpl("BOX2", 20); // Instancia 2 na Heap

        b1 = b2; // Instancia 1 fica INALCANCAVEL -> Elegivel para o Garbage Collector!
        b2 = null; // Instancia 2 ainda e alcancavel atraves de b1
    }
}

APP03: Construtores, Sobrecarga e Encadeamento `this()` / `super()`

💡 Explicação Aprofundada da Matéria dos Slides:

Os construtores são blocos especiais de inicialização de instâncias na Heap. Se nenhum construtor for declarado, o compilador gera automaticamente o default constructor (público e sem parâmetros). Ao escrever pelo menos um construtor explícito, a geração automática do construtor por defeito é **cancelada**.

Pergunta de Exame Construtores, Construtor por Defeito e Encadeamento (1,5 valores)

Explique o conceito de construtores em Java, descrevendo as suas características e regras de definição. Distinga entre construtor por defeito, construtor parametrizado e encadeamento de construtores (com this(...) e super(...)). Esclareça o que acontece quando uma classe não define nenhum construtor explicitamente e apresente um exemplo de código.

📋 Resposta Modelo (1,5v): "Construtores e Encadeamento com this() e super()"

  1. Papel & Construtor por Defeito: Construtores configuram o estado inicial dos objetos na Heap via `new`. Se uma classe não declarar construtores, o compilador gera o construtor por defeito sem argumentos. Se for declarado qualquer construtor parametrizado, o compilador deixa de criar o construtor por defeito.
  2. Sobrecarga & Encadeamento (`this(...)`): A sobrecarga permite múltiplos construtores com parâmetros distintos. O encadeamento via `this(...)` chama outro construtor da própria classe para evitar duplicação de código.
  3. Restrição Sintática Exigida: As chamadas `this(...)` ou `super(...)` têm de ser obrigatoriamente a **PRIMEIRA instrução** do construtor e não podem ser usadas simultaneamente no mesmo construtor.

💻 Excerto de Código Ilustrativo:

public class AidBox {
    private String code;
    private String zone;

    // Construtor Parametrizado 1: delega no Construtor 2 via this(...)
    public AidBox(String code) {
        this(code, "Geral"); // Tem de ser a PRIMEIRA linha!
    }

    // Construtor Parametrizado 2
    public AidBox(String code, String zone) {
        this.code = code;
        this.zone = zone;
    }
}

APP04: Modificadores de Acesso & Imutabilidade com `final`

💡 Explicação Aprofundada da Matéria dos Slides:

O modificador final aplica restrições de imutabilidade consoante o elemento onde é declarado:

Pergunta de Exame O Modificador final em Java (1,5 valores)

Descreva o impacto e a finalidade da utilização da palavra reservada final quando aplicada a: (1) uma variável, (2) um método e (3) uma classe. Esclareça adicionalmente a diferença de comportamento de uma variável final quando esta armazena um tipo primitivo versus quando armazena um tipo de referência (objeto).

📋 Resposta Modelo (1,5v): "Impacto do Modificador final"

  1. Aplicação em Métodos e Classes:
    • Método `final`: Impede que o método seja sobreposto (*overridden*) por subclasses.
    • Classe `final`: Impede que a classe seja estendida/herda (`extends`), assegurando imutabilidade (ex: `String`).
  2. Variável `final` — Primitivos vs Referências:
    • Primitivo: O valor numérico/literal fica constante e inalterável após a primeira atribuição.
    • Referência (Objeto): O **endereço de memória (ponteiro)** fica imutável (impossível fazer novo `new`), contudo **o estado interno do objeto apontado pode ser modificado** através dos seus métodos mutadores.
  3. Inicialização Obrigatória: Variáveis `final` devem ser inicializadas na declaração ou obrigatoriamente no construtor da classe.

💻 Excerto de Código Ilustrativo:

public final class Constantes { // Classe final: Ninguem pode fazer 'extends Constantes'
    private final int maxCapacity = 100; // Primitivo final: valor inalteravel
    private final AidBoxImpl box = new AidBoxImpl("A1", 10); // Referencia final

    public void testar() {
        // maxCapacity = 200; -> ERRO DE COMPILACAO!
        // box = new AidBoxImpl("A2", 20); -> ERRO DE COMPILACAO! (ponteiro imutavel)

        box.setCapacity(99.0); // OK! O estado interno do objeto na Heap PODE ser alterado.
    }

    public final void metodoProtegido() { // Nao pode ser sobreposto em subclasses
        System.out.println("Seguro.");
    }
}

APP05: Membros Static, Enums, Wrappers & Cache Integer

💡 Explicação Aprofundada da Matéria dos Slides:

  • `static`: Membros pertencentes à classe (alocados na Metaspace). Não necessitam de instância na Heap.
  • `enum`: Tipos de constantes seguras. Têm construtores obrigatoriamente `private`.
  • Integer Cache: A JVM mantém cache de objetos `Integer` para valores entre **-128 e 127**. Fora desta gama, a comparação com `==` falha (usar sempre `.equals()`).

Pergunta de Exame Membros Estáticos (static) e Proibição do this/super (1,5 valores)

Discuta o modificador static em Java aplicado a atributos e a métodos. Descreva as diferenças entre membros estáticos (de classe) e membros de instância no que diz respeito ao seu ciclo de vida e alocação de memória. Justifique explicitamente por que razão as palavras reservadas this e super não podem ser utilizadas dentro de métodos estáticos.

📋 Resposta Modelo (1,5v): "Membros Static e Proibição de this e super"

  1. Static vs Instância: Membros `static` pertencem à classe (área de classes / Metaspace) e existe uma única cópia partilhada por todas as instâncias. Membros de instância pertencem aos objetos individuais alocados na Heap.
  2. Invocações Estáticas: Métodos estáticos podem ser executados via `NomeClasse.metodo()` sem necessidade de instanciar objetos com `new`.
  3. Proibição de `this` e `super`: Dado que `this` representa o ponteiro para a instância corrente na Heap e `super` a sua superclasse, e os métodos estáticos executam fora do contexto de qualquer objeto, a utilização de `this` ou `super` no escopo estático é **estritamente proibida pelo compilador**.

💻 Excerto de Código Ilustrativo:

public class Contador {
    private static int totalInstancias = 0; // Partilhado por TODAS as instancias
    private int idInstancia; // Especifico de cada objeto

    public Contador() {
        totalInstancias++;
        this.idInstancia = totalInstancias;
    }

    public static int getTotalInstancias() {
        // System.out.println(this.idInstancia); -> ERRO COMPILACAO! 'this' proibido!
        return totalInstancias;
    }
}

Pergunta de Exame Tipos Enumerados (Enum) em Java (1,5 valores)

Explique o conceito de tipos enumerados (enum) em Java. Descreva as vantagens de utilizar enum em vez de constantes inteiras ou Strings. Demonstre como um enum pode ter atributos, construtores privados e métodos com um exemplo prático.

📋 Resposta Modelo (1,5v): "Tipos Enumerados (Enum)"

  1. Conceito & Vantagens: Enums representam conjuntos fixos de constantes tipificadas. Oferecem segurança de tipos (*Type Safety*) em tempo de compilação, legibilidade e suporte para blocos `switch` e comparação nula-segura com `==`.
  2. Estrutura Interna: Podem possuir atributos de instância, métodos e construtores. Os **construtores de um enum são obrigatoriamente privados (`private`)**, sendo invocados automaticamente aquando da definição das constantes.
  3. Exemplo Prático: Ex: `public enum State { ENABLED("Ativo"), DISABLED("Inativo"); private final String label; private State(String l) { this.label = l; } }`

💻 Excerto de Código Ilustrativo:

public enum ItemType {
    PERISHABLE_FOOD("Perecivel"),
    NON_PERISHABLE_FOOD("Nao Perecivel");

    private final String descricao;

    // Construtor OBRIGATORIAMENTE privado
    private ItemType(String descricao) {
        this.descricao = descricao;
    }

Pergunta de Exame Classes Wrapper, Autoboxing e Cache Integer (1,5 valores)

O que são classes Wrapper em Java e qual o seu propósito? Explique os conceitos de Autoboxing e Unboxing e discuta o problema de desempenho e o risco da comparação de valores com o operador == devido à cache de Integer.

📋 Resposta Modelo (1,5v): "Wrappers, Autoboxing e Armadilha do Integer Cache"

  1. Propósito dos Wrappers: Envolvem tipos primitivos em objetos (ex: `int` -> `Integer`), permitindo a sua utilização em estruturas como Generics e Coleções (`ArrayList`).
  2. Autoboxing & Unboxing: Conversões automáticas entre primitivos e Wrappers efetuadas pelo compilador. Autoboxing intensivo em ciclos provoca alocações maciças na Heap, penalizando o Garbage Collector.
  3. Armadilha do Integer Cache: A JVM mantém uma cache de instâncias de `Integer` apenas para valores entre **-128 e 127**. Dentro dessa gama, `==` funciona porque reaproveita a mesma referência. Fora de -128..127, `==` falha por comparar ponteiros distintos na Heap (deve usar-se **sempre `.equals()`**).

💻 Excerto de Código Ilustrativo:

public class TestCache {
    public static void main(String[] args) {
        Integer a = 100, b = 100;
        System.out.println(a == b); // TRUE (Dentro da cache -128..127, mesma referencia)

        Integer x = 200, y = 200;
        System.out.println(x == y); // FALSE! (Fora da cache! Instancias distintas na Heap)
        System.out.println(x.equals(y)); // TRUE (Comparacao logica correta)
    }
}

APP06: Arrays de Objetos, Composição & Clonagem (Shallow vs Deep Copy)

💡 Explicação Aprofundada da Matéria dos Slides:

Um array de objetos em Java é um objeto na Heap cujas posições armazenam ponteiros de referência, inicializados por defeito a null. Redimensionar um array exige alocar um novo array maior e copiar os ponteiros.

Pergunta de Exame Arrays de Objetos e Redimensionamento (1,5 valores)

Explique o conceito de arrays de objetos em Java, distinguindo entre a criação do array e a criação dos objetos que o compõem. Descreva os cuidados necessários ao manipular arrays de objetos (posições nulas) e como se pode redimensionar um array.

📋 Resposta Modelo (1,5v): "Arrays de Objetos e Manipulação de Memória"

  1. Instanciação em 2 Etapas: Executar `Container[] arr = new Container[5];` apenas aloca o array na Heap com 5 posições a `null`. É imperativo instanciar cada posição com `new ContainerImpl(...)` para evitar `NullPointerException`.
  2. Tamanho Fixo na Heap: Arrays em Java possuem dimensão imutável após a alocação.
  3. Técnica de Redimensionamento: Para expandir a capacidade, cria-se um novo array com dimensão superior e copiam-se os elementos (ex: via `System.arraycopy` ou `Arrays.copyOf`).

💻 Excerto de Código Ilustrativo:

public class GestaoArrays {
    public void executar() {
        Container[] arr = new Container[3]; // Etapa 1: Array criado com 3 posicoes NULL
        // arr[0].getCode(); -> Lanca NullPointerException!

        arr[0] = new ContainerImpl("C1"); // Etapa 2: Instanciacao do objeto individual

        // Redimensionamento de Array de tamanho fixo
        Container[] novoArr = java.util.Arrays.copyOf(arr, arr.length * 2); // Duplica tamanho
    }
}

Pergunta de Exame Composição vs Herança (1,5 valores)

Explique as diferenças entre Composição e Herança em Java, descrevendo quando cada mecanismo é mais adequado. Justifique o princípio de que se deve 'favorecer a composição em detrimento da herança' (problemas de forte acoplamento e quebra de encapsulamento).

📋 Resposta Modelo (1,5v): "Composição vs Herança"

  1. Herança ("É UM" / White-box): Subclasse estende a superclasse (`extends`). Cria um **acoplamento forte** (tight coupling) onde alterações na superclasse podem quebrar as subclasses (problema da superclasse frágil).
  2. Composição ("TEM UM" / Black-box): Uma classe contem referências para instâncias de outras classes como atributos. Mantém acoplamento fraco e encapsulamento total.
  3. Favorecer a Composição: A composição permite alterar comportamentos dinamicamente em tempo de execução e facilita os testes unitários sem violar o encapsulamento interno das classes.

💻 Excerto de Código Ilustrativo:

// COMPOSICAO: Veiculo TEM UM Motor (Has-A). Acoplamento fraco.
public class Veiculo {
    private Motor motor; // Atributo de composicao

    public Veiculo(Motor motor) {
        this.motor = motor;
    }
    public void arrancar() {
        this.motor.ligar(); // Delega a acao no motor
    }
}

Pergunta de Exame Shallow Copy vs Deep Copy (1,5 valores)

Explique os conceitos de Shallow Copy (cópia superficial) e Deep Copy (cópia profunda) na instanciação e clonagem de objetos em Java. Discuta os problemas que podem surgir ao utilizar Shallow Copy em objetos com referências mutáveis e exemplifique uma Deep Copy.

📋 Resposta Modelo (1,5v): "Shallow Copy vs Deep Copy"

  1. Shallow Copy (Cópia Superficial): Copia apenas os valores dos campos. Para referências de objetos, copia os ponteiros, fazendo com que o objeto original e a cópia partilhem as **mesmas instâncias internas na Heap**. Alterar o estado interno de um afeta o outro.
  2. Deep Copy (Cópia Profunda): Aloca novos objetos independentes na Heap para todas as referências mutáveis internas, duplicando a árvore completa de dados.
  3. Implementação Correta: Exige a duplicação manual de arrays ou objetos contidos no construtor de cópia (ex: `this.containers = new Container[other.containers.length];` seguido de novas instâncias para cada posição).

💻 Excerto de Código Ilustrativo:

public class AidBox {
    private Container[] containers;

    // DEEP COPY: Instancia um novo array E novos objetos para cada posicao
    public AidBox(AidBox original) {
        this.containers = new Container[original.containers.length];
        for (int i = 0; i < original.containers.length; i++) {
            if (original.containers[i] != null) {
                this.containers[i] = new ContainerImpl(original.containers[i].getCode()); // Novo objeto Heap!
            }
        }
    }
}

APP07: Herança e Reutilização com `super`

💡 Explicação Aprofundada da Matéria dos Slides:

Herança (extends) permite partilhar atributos e métodos. A palavra reservada super acede a membros e construtores da superclasse.

Pergunta de Exame Herança e a Palavra Reservada super (1,5 valores)

Explique o conceito de herança em Java. Descreva o papel da palavra reservada super e os diferentes contextos em que pode ser utilizada (construtor e métodos). Discuta as limitações da herança simples em Java e como as interfaces contornam essas limitações.

📋 Resposta Modelo (1,5v): "Herança e o papel de super"

  1. Herança Simples (`extends`): Em Java, uma classe só pode estender diretamente uma única superclasse.
  2. Uso da palavra `super`:
    • No construtor: `super(...)` chama o construtor da superclasse e tem de ser a **primeira linha do construtor**.
    • Em métodos: `super.metodo()` invoca a implementação original da superclasse que foi sobreposta na subclasse.
  3. Contorno com Interfaces: Para contornar a limitação da herança simples de código, Java permite que uma classe implemente múltiplas interfaces, alcançando herança múltipla de tipo.

💻 Excerto de Código Ilustrativo:

public class Veiculo {
    private String matricula;
    public Veiculo(String matricula) { this.matricula = matricula; }
    public void exibirInfo() { System.out.println("Matricula: " + matricula); }
}

public class Camiao extends Veiculo {
    private double cargaMax;

    public Camiao(String matricula, double cargaMax) {
        super(matricula); // Invoca construtor da superclasse (Primeira linha!)
        this.cargaMax = cargaMax;
    }

    @Override
    public void exibirInfo() {
        super.exibirInfo(); // Invoca o metodo original da superclasse
        System.out.println("Carga Max: " + cargaMax);
    }
}

Explique detalhadamente as diferenças entre classes abstratas e interfaces em Java. Em que situações é mais adequado optar por uma classe abstrata e em que situações é preferível uma interface? 📋 Resposta Modelo (1,5v): "Classes Abstratas vs Interfaces"

  1. Classes Abstratas (`extends`): Não admitem `new`. Suportam herança simples, atributos de instância mutáveis, construtores e métodos concretos/abstratos. Adequadas para famílias de classes com relação "É UM" e partilha de estado/código.
  2. Interfaces (`implements`): Contratos puros de comportamento ("É CAPAZ DE"). Permitem herança múltipla de tipo, **não possuem construtores** e os seus atributos são exclusivamente `public static final`.
  3. Quando Escolher: Optar por Classe Abstrata ao desenhar uma hierarquia estreita com código e estado comuns. Optar por Interface para definir capacidades transversais a classes não relacionadas na hierarquia de herança.

💻 Excerto de Código Ilustrativo:

// CLASSE ABSTRATA: Heranca simples, estado mutavel e construtores
public abstract class VeiculoAbstrato {
    private String code; // Estado de instancia
    public VeiculoAbstrato(String code) { this.code = code; } // Construtor
    public abstract double calcularAutonomia(); // Metodo abstrato
}

// INTERFACE: Contrato puro, sem construtores, heranca multipla
public interface Refrigerated {
    double getMinTemperature(); // Metodo abstrato (public implicitamente)
}

Pergunta de Exame Polimorfismo: Sobrecarga vs Sobreposição e Despacho Dinâmico (1,5 valores)

Explique o conceito de polimorfismo em Java, distinguindo entre polimorfismo de sobrecarga (overloading) e polimorfismo de sobreposição (overriding). Descreva o funcionamento do mecanismo de Despacho Dinâmico (Dynamic Binding) executado pela JVM em tempo de execução.

📋 Resposta Modelo (1,5v): "Sobrecarga, Sobreposição e Despacho Dinâmico"

  1. Sobrecarga (Overloading - Estático / Compile-Time): Ocorre na mesma classe com múltiplos métodos de mesmo nome e assinaturas diferentes (parâmetros). A resolução é feia em tempo de **compilação**.
  2. Sobreposição (Overriding - Dinâmico / Runtime): Ocorre numa subclasse que redefini um método herdado mantendo a mesma assinatura (`@Override`).
  3. Despacho Dinâmico (Dynamic Method Dispatch): A decisão de qual método executar ocorre em tempo de **execução** (runtime) pela JVM com base no tipo real da instância alocada na Heap, e não no tipo da variável de referência.

💻 Excerto de Código Ilustrativo:

public class Calculadora {
    // SOBRECARGA (Overloading): mesmo nome, parametros diferentes (Compile-time)
    public int somar(int a, int b) { return a + b; }
    public double somar(double a, double b) { return a + b; }
}

public class TestePolimorfismo {
    public static void main(String[] args) {
        VeiculoAbstrato v = new Camiao("C1", 500); // Upcasting
        v.calcularAutonomia(); // DESPACHO DINAMICO: Executa o metodo de Camiao em runtime!
    }
}

APP09: Interfaces e Métodos Default (Java 8+)

💡 Explicação Aprofundada da Matéria dos Slides:

Interfaces aceitam métodos `default` com corpo. Em caso de conflito de métodos `default` idênticos em duas interfaces implementadas, a classe é **obrigada a sobrescrever (`@Override`) o método** para resolver a ambiguidade.

📋 Resposta Modelo (1,5v): "Interfaces e Conflitos de Métodos Default"

  1. Evolução das Interfaces: Os métodos `default` permitem adicionar novas funcionalidades com implementação padrão sem quebrar as classes existentes.
  2. Herança Múltipla de Tipo: Uma classe Java pode implementar N interfaces simultaneamente.
  3. Resolução do Problema dos "Diamantes": Se duas interfaces fornecerem o mesmo método `default`, o compilador gera um erro de ambiguidade, obrigando a classe a sobrescrever o método e resolver explicitamente via `InterfaceA.super.metodo()`.

💻 Excerto de Código Ilustrativo:

public interface A {
    default void log() { System.out.println("Log A"); }
}
public interface B {
    default void log() { System.out.println("Log B"); }
}

public class Impl implements A, B {
    @Override
    public void log() {
        A.super.log(); // Resolve a ambiguidade invocando explicitamente a interface A
    }
}

APP10: Hierarquia Object, Identidade vs Igualdade, Casting e HashCode

Exame Época Normal 2025/2026 Identidade, Igualdade e toString() (1,5 valores)

Distinga os conceitos de identidade e de igualdade de objetos em Java, esclarecendo a diferença entre o operador == e o método equals(). Explique igualmente o papel do método toString(). Forneça um exemplo prático que demonstre a redefinição correta dos métodos equals() e toString() numa classe.

📋 Resposta Modelo (1,5v): "Identidade (==) vs Igualdade (equals) e toString()"

  1. Identidade Physical (`==`): Avalia se duas variáveis de referência apontam para a **mesma posição de memória Heap**.
  2. Igualdade Logical (`equals()`): Avalia se dois objetos possuem o **mesmo conteúdo lógico**. O método herdado de `Object` usa `==`, devendo ser redefinido.
  3. Papel do `toString()`: Devolve uma representação textual legível do estado interno do objeto (substituindo a string padrão `Classe@hashHex`).

💻 Excerto de Código Ilustrativo (Redefinição Padrão em 5 Passos):

public class AidBoxImpl {
    private String code;

    @Override
    public boolean equals(Object obj) {
        if (this == obj) return true;                  // 1. Mesma referencia Heap
        if (obj == null) return false;                 // 2. Nulo
        if (!(obj instanceof AidBoxImpl)) return false;// 3. Verificacao de Tipo
        AidBoxImpl other = (AidBoxImpl) obj;            // 4. Cast seguro
        return this.code.equals(other.code);            // 5. Comparacao logica do estado
    }

    @Override
    public String toString() {
        return "AidBox [code=" + code + "]";
    }
}

Exame Época Normal 2025/2026 Conversão de Tipos (Casting) e instanceof (1,5 valores)

Explique o conceito de conversão de tipos (casting) no contexto da herança e do polimorfismo. Discuta os riscos associados a conversões incorretas e as situações em que cada tipo de conversão é apropriado. Ilustre com um exemplo prático que demonstre as conversões.

📋 Resposta Modelo (1,5v): "Upcasting, Downcasting e instanceof"

  1. Upcasting: Subclasse -> Superclasse (automático e 100% seguro).
  2. Downcasting: Superclasse -> Subclasse (explícito e arriscado, lança `ClassCastException` em runtime se o tipo for incompatível).
  3. Operador `instanceof`: Valida o tipo real na Heap antes de efetuar a conversão descendente.

💻 Excerto de Código Ilustrativo:

public class TesteCasting {
    public static void processar(Veiculo v) { // Upcasting automatico
        // Protecao com instanceof antes de fazer Downcasting
        if (v instanceof Camiao) {
            Camiao c = (Camiao) v; // Downcasting seguro
            System.out.println(c.getCargaMax());
        }
    }
}

Pergunta de Exame instanceof vs getClass() no equals() (1,5 valores)

Compare detalhadamente a utilização de instanceof com a utilização de getClass() para verificação de tipos em Java. Discuta as diferenças de comportamento na presença de herança e interfaces.

📋 Resposta Modelo (1,5v): "instanceof vs getClass()"

  1. `instanceof` (Flexível / Polimórfico): Avalia se o objeto é uma instância da classe especificada ou de qualquer subclasse/interface implementada.
  2. `getClass()` (Exato / Restritivo): Avalia a correspondência **exata de classe**. Devolve `false` se o objeto for de uma subclasse.
  3. Aplicação no `equals()`: Utilizar `instanceof` quando a igualdade é definida ao nível da interface ou superclasse. Utilizar `getClass()` para garantir simetria rigorosa na herança.

💻 Excerto de Código Ilustrativo:

Veiculo v = new Camiao("C1", 100);

System.out.println(v instanceof Veiculo); // TRUE (Camiao E UM Veiculo)
System.out.println(v.getClass() == Veiculo.class); // FALSE (Classe exata e Camiao.class!)

Pergunta de Exame Contrato estrito entre equals() e hashCode() (1,5 valores)

Explique o contrato estrito existente entre os métodos equals() e hashCode() em Java. Analise as consequências desastrosas que ocorrem na aplicação quando o método equals() é redefinido sem redefinir o método hashCode() em coleções baseadas em hashing (HashSet / HashMap).

📋 Resposta Modelo (1,5v): "Contrato equals() e hashCode()"

  1. O Contrato Estrito: Se dois objetos forem iguais segundo o método `equals()`, eles **DEVEM obrigatoriamente devolver o mesmo valor inteiro no método `hashCode()`**. (O inverso não é obrigatoriamente verdadeiro).
  2. Consecuência da Violação: Redefinir `equals()` sem redefinir `hashCode()` faz com que dois objetos logicamente iguais gerem códigos de hash diferentes.
  3. Impacto em Coleções de Hashing (`HashSet`/`HashMap`): A coleção colocará os objetos em *buckets* de memória distintos. Ao tentar pesquisar ou remover o objeto, a coleção não o encontrará, violando o comportamento de conjuntos e tabelas de hash.

💻 Excerto de Código Ilustrativo:

public class AidBoxImpl {
    private String code;

    @Override
    public boolean equals(Object obj) {
        if (this == obj) return true;
        if (!(obj instanceof AidBoxImpl)) return false;
        return this.code.equals(((AidBoxImpl)obj).code);
    }

    @Override
    public int hashCode() {
        return java.util.Objects.hash(code); // OBRIGATORIO: Garante hash idêntico para objetos iguais!
    }
}

Pergunta de Exame Exceções Checked vs Unchecked, bloco finally e AutoCloseable (1,5 valores)

Explique detalhadamente o mecanismo de tratamento de exceções em Java. Distinga exceções verificadas (Checked Exceptions) de exceções não verificadas (Unchecked Exceptions / RuntimeException). Descreva o fluxo do bloco try-catch-finally e o comportamento do finally caso exista uma instrução return no try. Explique a utilidade do try-with-resources e a interface AutoCloseable.

📋 Resposta Modelo (1,5v): "Checked vs Unchecked, finally e try-with-resources"

  1. Checked vs Unchecked:
    • Checked Exceptions (`Exception`): O compilador **exige obrigatoriamente** tratamento (`try-catch`) ou declaração (`throws`). Representam erros ambientais recuperáveis.
    • Unchecked Exceptions (`RuntimeException`): O compilador não exige verificação. Representam erros de lógica e programação.
  2. Fluxo do Bloco `finally`: O bloco `finally` executa **SEMPRE**, mesmo que ocorram exceções ou que exista uma instrução `return` dentro do bloco `try` ou `catch`.
  3. `try-with-resources` & `AutoCloseable`: Garante o fecho automático de recursos (streams, conexões) ao sair do bloco `try`, desde que o recurso implemente a interface `AutoCloseable`, eliminando a necessidade de código repetitivo no `finally`.

💻 Excerto de Código Ilustrativo:

public class TesteExcecoes {
    public int testarFinally() {
        try {
            return 10; // Prepara retorno de 10
        } finally {
            System.out.println("Executa SEMPRE antes do metodo retornar!");
        }
    }

    // try-with-resources com AutoCloseable
    public void lerFicheiro(String path) throws java.io.IOException {
        try (java.io.FileReader fr = new java.io.FileReader(path)) {
            fr.read();
        } // 'fr' e FECHADO AUTOMATICAMENTE aqui mesmo com excecoes!
    }
}

APP12: I/O (Streams) & Serialização

💡 Explicação Aprofundada da Matéria dos Slides:

  • Byte Streams (`InputStream`/`OutputStream`): 8 bits (dados binários crús).
  • Character Streams (`Reader`/`Writer`): 16 bits Unicode (texto legível UTF-8).
  • Serialização: Converte o estado do objeto na Heap em fluxo de bytes (`Serializable`). O modificador `transient` omite atributos da serialização por segurança.

Pergunta de Exame Byte Streams vs Character Streams (1,5 valores)

A biblioteca de I/O do Java divide-se em classes orientadas a bytes e classes orientadas a caracteres. Explique a diferença fundamental entre estas duas famílias de classes e indique em que cenários práticos é adequada a utilização de cada uma.

📋 Resposta Modelo (1,5v): "Byte Streams vs Character Streams"

  1. Byte Streams (`InputStream`/`OutputStream`): Manipulam dados binários crús em pacotes de 8 bits. Indicadas para imagens, ficheiros compactados (.zip), áudio/vídeo e transmissão na rede.
  2. Character Streams (`Reader`/`Writer`): Manipulam texto formatado em caracteres Unicode de 16 bits com conversão automática de codificação (ex: UTF-8). Indicadas para ficheiros de texto (.txt, .json, .xml).

💻 Excerto de Código Ilustrativo:

// Byte Stream (dados binarios de 8 bits)
try (java.io.FileInputStream fis = new java.io.FileInputStream("imagem.png")) {
    int byteLido = fis.read();
}

// Character Stream (texto Unicode de 16 bits)
try (java.io.FileReader fr = new java.io.FileReader("dados.txt")) {
    int charLido = fr.read();
}

Pergunta de Exame Serialização, transient e serialVersionUID (1,5 valores)

O que é a Serialização de objetos em Java e qual a sua finalidade? Explique como se sinaliza que uma classe é elegível para serialização e descreva a finalidade do modificador transient e do identificador serialVersionUID.

📋 Resposta Modelo (1,5v): "Serialização, transient e serialVersionUID"

  1. Serialização & Interface Marcadora: Processo de conversão do estado do objeto em bytes para persistência/transmissão. Exige implementar a interface marcadora `java.io.Serializable`.
  2. Modificador `transient`: Assinala atributos que **NÃO devem ser serializados** (ex: palavras-passe ou dados temporários recalculáveis).
  3. Identificador `serialVersionUID`: Identificador numérico que garante a compatibilidade de versões da classe durante o processo de deserialização, prevenindo exceções `InvalidClassException`.

💻 Excerto de Código Ilustrativo:

public class Usuario implements java.io.Serializable {
    // Identificador de versao para deserializacao
    private static final long serialVersionUID = 1L;

    private String nome;
    private transient String password; // transient: OMITIDO da serializacao por seguranca!

    public Usuario(String nome, String password) {
        this.nome = nome;
        this.password = password;
    }
}
