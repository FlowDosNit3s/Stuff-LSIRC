APP01: Paradigma Orientado a Objetos e Pilares

💡 Explicação Aprofundada da Matéria:

No paradigma imperativo/procedimental (como C), o software divide-se entre dados isolados e funções operando sobre esses dados. Em Programação Orientada a Objetos (POO), o software é concebido como um conjunto de entidades autónomas designadas **Objetos**, que agregam o **estado** (atributos) e o **comportamento** (métodos).

  • Classe: Molde abstrato que define a estrutura de dados e comportamento de um novo tipo.
  • Objeto / Instância: Entidade concreta alocada na memória Heap através do operador `new`.

Os 4 Pilares da POO:

  1. Abstração: Modelação de entidades do mundo real capturando apenas os aspetos e comportamentos estritamente relevantes para o problema.
  2. Encapsulamento: Ocultação dos detalhes internos de implementação e proteção do estado através de visibilidade privada (`private`) e métodos acessores públicos (`getters`/`setters`).
  3. Herança: Reutilização hierárquica de código onde subclasses herdam atributos e métodos da superclasse (`extends`).
  4. Polimorfismo: Capacidade de responder de forma distinta à mesma invocação de método consoante a instância concreta alocada na Heap.

💻 Código Teórico Demonstrativo:

public class AidBoxImpl {
    private String code; // Estado encapsulado
    private double capacity;

    public AidBoxImpl(String code, double capacity) {
        this.code = code;
        this.capacity = capacity;
    }
    public double getCapacity() { return this.capacity; }
}

📋 Resposta Modelo (1,5v): "Encapsulamento e Modificadores"

  1. Conceito: Encapsulamento é a ocultação do estado interno de um objeto, controlando o acesso exclusivamente por métodos públicos.
  2. Mecanismo: Atributos declarados como `private` com métodos de acesso (`getters`/`setters`) contendo validação defensiva.
  3. Má Prática Public: Permite que código externo injete valores inválidos (ex: capacidade negativa) sem validação, violando a integridade das regras de negócio.

APP02: Tipos de Dados e Memória JVM (Stack vs Heap)

💡 Explicação Aprofundada da Matéria:

A JVM divide a memória em duas regiões operacionais principais:

  • Stack (Pilha de Execução): Organizada em quadros por Thread. Armazena variáveis locais, primitivos literais e referências para a Heap. É gerida com desalocação automática instantânea ao sair do método.
  • Heap (Memória Dinâmica): Área de memória global onde residem **todos os objetos concretos e arrays** criados com `new`. É gerida pelo Garbage Collector (GC).

Atributos de Instância (Heap) vs Variáveis Locais (Stack)

AspetoAtributos de Instância (Heap)Variáveis Locais (Stack)
Onde são declarados?No corpo da classe (fora de métodos).No corpo de métodos ou blocos.
Inicialização**AUTOMÁTICA pela JVM** (`0`, `0.0`, `false`, `null`).**NÃO HÁ INICIALIZAÇÃO**.
Efeito de LeituraDevolve o valor por defeito sem erro.**Erro de Compilação** se lida sem inicialização.

💻 Código Teórico Demonstrativo:

public class TesteMemoria {
    private int atributoHeap; // Inicializado AUTOMATICAMENTE a 0 pela JVM

    public void executar() {
        int varStack; // NÃO É inicializada!
        System.out.println(this.atributoHeap); // Imprime 0 (OK)
        // System.out.println(varStack); -> ERRO DE COMPILAÇÃO!
    }
}

APP03: Construtores, Sobrecarga e Encadeamento `this()`

💡 Explicação Aprofundada da Matéria:

Construtores inicializam o estado dos objetos na Heap. Se nenhum for escrito, o compilador gera o *default constructor* público sem argumentos. Ao declarar pelo menos um construtor, o compilador omite a geração automática.

Sobrecarga: Declaração de múltiplos construtores com assinaturas de parâmetros diferentes. Encadeamento (`this()`): Invoca outro construtor da própria classe para evitar duplicação de código.

📋 Resposta Modelo (1,5v): "Construtores e Encadeamento com this()"

  1. Papel: Construtores configuram o estado inicial dos objetos alocados na Heap via `new`.
  2. Sobrecarga & Encadeamento: Sobrecarga aceita parâmetros diferentes. `this()` chama outro construtor da mesma classe para evitar duplicação de código.
  3. Restrição Sintática Exigida: `this(...)` tem de ser obrigatoriamente a **PRIMEIRA linha de código** no construtor e não pode ser usado simultaneamente com `super()`.

APP05: Membros Static, Final, Enums e Cache Integer

💡 Explicação Aprofundada da Matéria:

  • `static`: Membros de classe partilhados por todas as instâncias. Métodos estáticos não possuem contexto de instância na Heap, sendo o uso de `this` ou `super` proibido por compilação.
  • `final`: Primitivos (valor imutável); Referências (ponteiro imutável, mas estado do objeto mutável); Métodos (impede `@Override`); Classes (impede herança).
  • `enum`: Constantes tipificadas com construtor obrigatoriamente `private`.
  • Cache Integer: Cache mantida para valores de objetos `Integer` entre **-128 e 127**. Fora desta gama, `==` falha (usar sempre `.equals()`).

📋 Resposta Modelo (1,5v): "Static, Final e Cache Integer"

  1. Static & Proibição do `this`: Membros `static` pertencem à classe. Métodos `static` podem executar sem qualquer objeto alocado na Heap; como `this` representa a instância atual, a sua utilização em métodos estáticos é proibida por compilação.
  2. Impacto do Final: Em primitivos torna o valor imutável. Em objetos torna a referência imutável (sem novo `new`), mas o estado interno do objeto permanece mutável.
  3. Armadilha do Integer: O operador `==` compara referências. A JVM mantém cache de `Integer` apenas de **-128 a 127**. Fora dessa gama, `==` devolve `false` mesmo com números iguais (usar sempre `.equals()`).

APP06: Arrays de Objetos e Gestão de Memória

💡 Explicação Aprofundada para Teoria:

Executar `Container[] arr = new Container[5];` **NÃO aloca objetos Container na Heap**. Reserva apenas o array com 5 posições contendo `null`. É necessário instanciar cada posição individualmente com `new ContainerImpl(...)` para evitar `NullPointerException`.

APP07: Herança e Reutilização com `super`

💡 Explicação Aprofundada para Teoria:

Herança (`extends`) representa a relação "É UM". `super(...)` chama o construtor da superclasse e tem de ser obrigatoriamente a **PRIMEIRA linha** do construtor da subclasse.

APP08: Classes Abstratas vs Interfaces e Polimorfismo

💡 Explicação Aprofundada da Matéria:

Tabela comparativa detalhada entre Classes Abstratas e Interfaces:

📋 Resposta Modelo (1,5v): "Classes Abstratas vs Interfaces"

  1. Classes Abstratas (`extends`): Não levam `new`. Suportam herança simples, atributos de instância mutáveis, construtores e métodos abstratos/concretos. Ideais para a relação "É UM" com partilha de código e estado.
  2. Interfaces (`implements`): Contratos puros de comportamento ("É CAPAZ DE"). Permitem herança múltipla de tipos, **não possuem construtores** e os atributos são exclusivamente `public static final`.
  3. Polimorfismo Dinâmico (Late Binding): A decisão de qual método executar ocorre em tempo de **execução** (runtime) com base na instância real na Heap.

APP09: Interfaces e Métodos Default (Java 8+)

💡 Explicação Aprofundada para Teoria:

Interfaces aceitam métodos `default` com corpo. Em caso de conflito de métodos `default` idênticos em duas interfaces implementadas, a classe é **obrigada a sobrescrever (`@Override`) o método** para resolver a ambiguidade.

APP10: Hierarquia Object, Identidade vs Igualdade e Casting

📋 Resposta Modelo (1,5v): "Identidade (==) vs Igualdade (equals)"

  1. Identidade Physical (`==`): Avalia se duas variáveis de referência apontam para a **mesma posição de memória Heap**.
  2. Igualdade Logical (`equals()`): Avalia se dois objetos possuem o **mesmo conteúdo lógico**.
  3. Negligenciar `equals()`: O método herdado de `Object` usa `==`. Se não for redefinido, dois objetos distintos com dados idênticos serão considerados erradamente diferentes.

📋 Resposta Modelo (1,5v): "Upcasting, Downcasting e instanceof"

  1. Upcasting: Subclasse -> Superclasse (automático e 100% seguro).
  2. Downcasting: Superclasse -> Subclasse (explícito e arriscado, lança `ClassCastException`).
  3. Operador `instanceof`: Valida o tipo real na Heap em runtime antes de converter.

APP11: Gestão de Exceções (Checked vs Unchecked e `finally`)

💡 Explicação Aprofundada para Teoria:

                     java.lang.Throwable

             |                                 |
       java.lang.Error               java.lang.Exception
                                               |
                             +-----------------+-----------------+
                             |                                   |
                   Checked Exceptions                 RuntimeException
                (IOException, etc.)                  (Unchecked Exceptions)

📋 Resposta Modelo (1,5v): "Checked vs Unchecked Exceptions e finally"

  1. Checked Exceptions (`Exception`): Erros ambientais recuperáveis. O compilador **exige obrigatoriamente** tratamento (`try-catch`) ou declaração (`throws`).
  2. Unchecked Exceptions (`RuntimeException`): Bugs de lógica. Compilador não exige verificação.
  3. Bloco `finally`: Executa **SEMPRE**, mesmo com exceções ou instrução `return` no `try`/`catch`.

APP12: I/O (Streams) & Serialização

💡 Explicação Aprofundada para Teoria:

  • Byte Streams (`InputStream`/`OutputStream`): 8 bits (dados binários).
  • Character Streams (`Reader`/`Writer`): 16 bits Unicode (texto legível UTF-8).
  • Serialização: Converte o estado do objeto na Heap em fluxo de bytes (`Serializable`). O modificador `transient` omite atributos da serialização por segurança.

📋 Resposta Modelo (1,5v): "Byte vs Character Streams e Serialização"

  1. Byte Streams vs Character Streams: Byte Streams manipulam dados binários crús em pacotes de 8 bits. Character Streams manipulam texto de 16 bits Unicode com codificação automática de carateres (ex: UTF-8).
  2. Mecanismo de Serialização: Processo de conversão do estado de um objeto em bytes para gravação/transmissão (`Serializable`). `transient` impede a serialização de dados sensíveis e `serialVersionUID` valida a compatibilidade de versões da classe.
