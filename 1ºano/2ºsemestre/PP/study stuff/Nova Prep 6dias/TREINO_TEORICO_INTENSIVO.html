1. Encapsulamento & Modificadores de Acesso
Explique detalhadamente o conceito de encapsulamento em Programação Orientada a Objetos. Descreva como os modificadores de acesso (private, protected, default, public) contribuem para este princípio. Justifique por que razão o acesso direto aos atributos de uma classe é considerado uma má prática e ilustre o uso correto com um exemplo prático. 🔥 95% Prob.
  • O Essencial: Encapsulamento é a ocultação da estrutura interna de um objeto. O estado (atributos) não deve ser acedido diretamente, mas sim manipulado através de métodos controlados (getters/setters).
  • Modificadores: private (só na classe), default (só no pacote), protected (pacote + subclasses), public (em todo o lado).
  • Porquê não public? Porque quebra o encapsulamento. Código externo poderia injetar valores inválidos (ex: capacidade negativa), violando as regras de negócio.

💻 Exemplo Prático

public class Contentor {
    private double capacidade; // Encapsulado!

    public void setCapacidade(double c) {
        if (c <= 0) throw new IllegalArgumentException("Inválido");
        this.capacidade = c; // Acesso validado defensivamente
    }
}

2. Construtores: invocação com `this()` e `super()`
Discuta a finalidade dos construtores na instanciação de objetos em Java. Explique o conceito de sobrecarga de construtores e demonstre como o encadeamento de construtores pode ser alcançado através das palavras reservadas this() e super(). Esclareça as restrições sintáticas associadas à utilização destas invocações. ⚡ 85% Prob.
  • O Essencial: Construtores inicializam o estado de um objeto na Heap. Se nenhum for escrito, o compilador gera o default constructor vazio.
  • Sobrecarga e Encadeamento: Podemos ter múltiplos construtores (com parâmetros diferentes). this() chama outro construtor da própria classe. super() chama o construtor da superclasse.
  • Restrição Sintática Crítica: As invocações a this() ou super() têm de ser obrigatoriamente a primeira linha de código dentro do construtor, e nunca podem ser usadas em simultâneo no mesmo construtor.

💻 Exemplo Prático

public class Veiculo {
    public Veiculo(String mat) { /* inicializa */ }
}
public class Camiao extends Veiculo {
    private double tara;
    
    public Camiao(String mat, double tara) {
        super(mat); // Obrigatório ser a 1ª linha (chama Veiculo)
        this.tara = tara;
    }
    
    public Camiao(String mat) {
        this(mat, 1000.0); // Encadeamento: chama o outro construtor de Camiao
    }
}

3. Variáveis de Classe (static) vs Variáveis de Instância
Distinga detalhadamente as Variáveis de Instância das Variáveis de Classe no contexto da linguagem Java, incidindo sobre o modificador static. Esclareça as razões pelas quais a utilização da palavra reservada this não é permitida no corpo de métodos declarados como estáticos e ilustre a sua resposta com um exemplo estruturado. ⚡ 85% Prob.
  • O Essencial: Variáveis de instância pertencem a cada objeto (alocadas na Heap por cada new). Variáveis de classe (static) são únicas e partilhadas por todos os objetos da classe.
  • Uso do `this`: O operador this refere-se ao "objeto atual que invocou o método". Como métodos estáticos pertencem à classe e podem ser executados sem que nenhum objeto exista em memória, não há nenhum objeto atual ao qual o this possa apontar (logo, é proibido).

💻 Exemplo Prático

public class AidBox {
    private String code; // Instância (cada caixa tem o seu)
    private static int totalBoxes = 0; // Classe (comum a todas as caixas)

    public static int getTotal() {
        // return this.code; -> ERRO DE COMPILAÇÃO! Não há "this" aqui.
        return totalBoxes; // OK
    }
}

4. Modificador final (Primitivos vs Referências)
Explique o impacto e a finalidade da utilização do modificador final em Java. Esclareça detalhadamente a diferença de comportamento de uma variável final quando esta armazena um tipo primitivo versus quando armazena uma referência para um objeto ou array. Fundamente a sua explicação com um exemplo de código representativo. ⚡ 80% Prob.
  • O Essencial: O modificador final impede a reatribuição da variável (torna-se constante após inicializada), impede a redefinição de métodos (override) e proíbe a herança de classes.
  • Primitivos: O valor numérico fica inalterável na Stack.
  • Referências: Apenas o "endereço de memória" para a Heap fica inalterável. Não é possível reatribuir um novo objeto com new, mas o estado interno do objeto é mutável.

💻 Exemplo Prático

final int MAX = 100;
// MAX = 200; -> ERRO!

final Contentor c = new Contentor(100);
// c = new Contentor(200); -> ERRO! Não pode mudar a referência.
c.setCapacidade(50); // OK! O interior do objeto não está bloqueado.

5. Memória (Stack/Heap), GC e NPE
Discuta o modelo de gestão de memória adotado pela Máquina Virtual Java (JVM), descrevendo minuciosamente o papel da Stack e da Heap. Explique o processo pelo qual o Garbage Collector elimina objetos inalcançáveis e elucide as causas que conduzem a uma NullPointerException. ⚡ 70% Prob.
  • Stack vs Heap: A Stack guarda variáveis locais (primitivos e referências) e os quadros de execução dos métodos por Thread. A Heap é a memória massiva onde residem todos os objetos concretos criados com new.
  • Garbage Collector (GC): Analisa periodicamente a Heap. Quando deteta objetos para os quais já não há nenhuma variável da Stack a apontar ("inalcançáveis"), liberta-os da memória RAM para prevenir leaks.
  • NullPointerException: Ocorre quando tentamos usar o "ponto" (invocar um método ou atributo) numa variável de referência que não está a apontar para nenhum objeto na Heap (ou seja, vale null). Previne-se com `if (obj != null)`.

6. Composição ("Tem Um") vs Herança ("É Um")
Distinga os conceitos de Composição e Herança enquanto mecanismos de reutilização de código no paradigma orientado a objetos. Esclareça sob que premissas arquiteturais o uso de Herança é considerado apropriado, comparando-o com a abordagem de Composição. Ilustre a sua resposta com um exemplo prático. 🔥 90% Prob.
  • Herança ("É UM" / Is-A): Cria uma forte ligação de identidade. Reutiliza código fazendo uma classe estender a outra (extends). Só deve ser usada se a relação for logicamente absoluta (ex: Camião É UM Veículo). Traz forte acoplamento e Java só permite herança simples.
  • Composição ("TEM UM" / Has-A): Cria uma ligação através de atributos. Uma classe contém instâncias de outras classes. Traz flexibilidade, baixo acoplamento e permite simular herança múltipla. Favorita nas boas práticas modernas de arquitetura ("Favor composition over inheritance").

💻 Exemplo Prático

// HERANÇA (Má escolha se um camião puder deixar de ser veículo?)
class Camiao extends Veiculo { ... }

// COMPOSIÇÃO (Boa escolha: um camião TEM um motor)
class Camiao {
    private Motor motor; // Delegação de responsabilidades
    public Camiao() { this.motor = new MotorV8(); }
}

7. Classes Abstratas vs Interfaces
Explique detalhadamente as diferenças entre classes abstratas e interfaces em Java. Em que situações é mais adequado optar por uma classe abstrata e em que situações é preferível uma interface? Justifique a sua resposta e evidencie as características distintivas de cada mecanismo. 🔥 99% Prob.
  • Classes Abstratas: Permitem definir estado (atributos não-estáticos), construtores e métodos com implementação. Sofrem a limitação da herança simples (uma classe só faz extends de uma abstrata). Ideal para modelar a hierarquia core de objetos relacionados intimamente.
  • Interfaces: Atuam como contratos 100% abstratos (até ao Java 8). Apenas contêm métodos públicos não implementados e constantes public static final. Uma classe pode implementar (implements) múltiplas interfaces. Ideal para partilhar capacidades/comportamentos entre classes não relacionadas (ex: `Serializavel`, `Imprimivel`).

8. Polimorfismo: Overloading vs Overriding
Explique o conceito de polimorfismo em Java, distinguindo clara e objetivamente o polimorfismo de sobrecarga (overloading) do polimorfismo de sobreposição (overriding). Descreva as regras de vinculação (binding) estática e dinâmica na JVM. 🔥 95% Prob.
  • Sobrecarga (Overloading / Polimorfismo Estático): Vários métodos com o mesmo nome na mesma classe, mas parâmetros diferentes. O compilador decide qual método chamar em tempo de compilação (Early Binding) com base no tipo das variáveis.
  • Sobreposição (Overriding / Polimorfismo Dinâmico): Uma subclasse redefine um método da superclasse com a mesma assinatura (usando @Override). A decisão de qual versão executar é tomada em tempo de execução (Dynamic Binding), dependendo do objeto real que foi instanciado na memória Heap, e não da variável que o guarda.
📌 Origem: Exame Real — Época Normal 2025/2026 (Pergunta Teórica 3 - Saída Confirmada)
9. Conversão de Tipos: Upcasting, Downcasting e `instanceof`
Aborde o conceito de conversão de tipos (casting) no contexto da herança. Distinga os mecanismos de upcasting e downcasting, discutindo criticamente os riscos associados à conversão para subclasses. Justifique a importância do operador instanceof. 🔥 95% Prob.
  • Upcasting: Tratar uma Subclasse pelo tipo da sua Superclasse (ou Interface). Ocorre implicitamente e de forma segura, pois a subclasse tem garantidamente tudo o que a superclasse tem.
  • Downcasting: Forçar uma variável de Superclasse a ser tratada como Subclasse. É perigoso (requer cast explícito `(Tipo)`). Se o objeto na memória não for da subclasse indicada, a JVM aborta o programa com um ClassCastException.
  • O operador `instanceof`: Permite perguntar "Este objeto na memória pertence a esta classe?" antes de realizar o downcasting, tornando a operação perfeitamente segura.

10. Métodos default em Interfaces e Conflito do Diamante
Compare o conceito de Interfaces Marcadoras com a utilização de Métodos default (introduzidos no Java 8) em interfaces. Explique como os métodos default permitem evoluir contratos existentes, e descreva a regra de resolução da JVM para o conflito do problema do diamante. 🟡 45% Prob.
  • Interfaces Marcadoras: Interfaces completamente vazias, sem métodos (ex: Serializable). Servem apenas para rotular ("marcar") a classe perante a JVM.
  • Métodos default: Métodos em interfaces que têm um corpo de código (comportamento padrão). Servem para adicionar novos métodos a interfaces antigas sem quebrar o código de quem já as implementava.
  • Problema do Diamante: Ocorre se uma classe implementar duas interfaces diferentes que possuam um método default com exatamente o mesmo nome. O Java obriga o programador a fazer o @Override desse método na classe, forçando a resolução explícita do conflito (ex: InterfaceA.super.metodo();).

11. Identidade (==) vs Igualdade (equals)
Distinga os conceitos de identidade física e igualdade lógica de objetos em Java, contrapondo o uso do operador relacional == com a invocação do método equals(). Justifique as consequências caso uma classe negligencie a redefinição obrigatória do método equals() herdado de Object. 🔥 99% Prob.
  • Identidade Física (==): Avalia se as duas variáveis de referência apontam literalmente para a mesma zona de memória na Heap. Não avalia os dados!
  • Igualdade Lógica (equals()): Avalia se as propriedades internas (estado lógico, ex: ID ou código) dos dois objetos distintos os tornam "iguais" para o negócio.
  • A consequência: A classe Object implementa o equals usando ==. Se não o redefinirmos (fizer override) na nossa classe, o equals não funcionará como igualdade lógica e duas instâncias criadas separadamente com os mesmos dados serão sempre consideradas diferentes.

12. Gestão de Exceções: Checked vs Unchecked e finally
Explique o paradigma de gestão de erros em Java através de exceções. Distinga categoricamente entre exceções verificadas (Checked Exceptions) e não verificadas (Unchecked Exceptions). Descreva a arquitetura de cada componente do bloco try-catch-finally, salientando o papel fulcral do finally. 🔥 95% Prob.
  • Checked Exceptions: Condições recuperáveis (falha de I/O, base de dados offline). O compilador exige obrigatoriamente que o programador capture o erro (`try-catch`) ou avise que o lança (`throws`). Extensões diretas de Exception.
  • Unchecked Exceptions: Erros de lógica de programação imprevisíveis (Index Out Of Bounds, Null Pointer). O compilador não obriga ao tratamento. Extensões de RuntimeException.
  • O bloco `finally`: Garante a execução do código contido independentemente de haver um erro ou de um return antecipado. Essencial para fechar recursos (ficheiros, bases de dados).

13. Tipos Enumerados (Enum)
Esclareça o conceito de tipos enumerados (enum) em Java e a sua superioridade perante a declaração tradicional de constantes estáticas. Explique a possibilidade de declaração de atributos, construtores e métodos internos a um enum, demonstrando as regras relativas ao modificador de acesso aplicável ao seu construtor. ⚡ 85% Prob.
  • O Essencial: enum define um conjunto restrito e finito de valores constantes tipificados com segurança em tempo de compilação (type-safe). Evita a passagem de strings ou inteiros inválidos.
  • Construtores de Enum: Os enumerados podem ter atributos internos e métodos. Contudo, o seu construtor deve ser obrigatoriamente privado (implicito ou explícito), impedindo a instanciação de novos valores fora da declaração do Enum.

    private AlertType(String desc) { // Construtor privado!
        this.description = desc;
    }
}

14. Classes Wrapper e a Armadilha da Cache
Apresente o conceito de classes Wrapper de envolvimento e o mecanismo de Autoboxing e Unboxing na linguagem Java. Discuta exaustivamente os riscos associados à utilização do operador de identidade == na comparação de instâncias da classe Integer, referenciando explicitamente o mecanismo interno de cache da JVM e os seus limites operacionais. ⚡ 75% Prob.
  • Wrappers & Autoboxing: Classes como Integer ou Double encapsulam primitivos para que possam ser usados como Objetos. Autoboxing é a conversão automática do compilador (ex: `Integer i = 10;`).
  • A Armadilha do == na Cache: Para poupar memória, a JVM mantém uma cache na Heap para todos os objetos Integer entre -128 e 127.
    - Para números nesta gama, o == funciona porque a referência apontada é a mesma.
    - Fora desta gama (ex: 200), a JVM aloca objetos distintos. O == devolverá false mesmo que logicamente sejam os dois 200. Por isso, usa-se obrigatoriamente equals().

15. Imutabilidade da String e o uso de StringBuilder
Avalie criticamente o conceito de imutabilidade associado à classe String em Java e descreva o funcionamento do mecanismo de String Pool alocado na Heap. Compare esta abordagem arquitetural com a utilização da classe StringBuilder, justificando a preferência por esta última em cenários de processamento iterativo intensivo de cadeias de caracteres. 🟡 60% Prob.
  • String e Pool: A classe String é 100% imutável. Alterar o seu valor através de concatenação (+) aloca sempre um novo objeto na memória, abandonando o anterior, num ciclo vicioso de criação de lixo e desperdício de processamento. Valores literais partilham a memória num "String Pool".
  • StringBuilder: Mantém um buffer de caracteres mutável. Métodos como .append() alteram a string no mesmo espaço de memória, sendo absurdamente mais eficiente em laços (for/while) massivos do que as Strings tradicionais.

16. Serialização: transient e serialVersionUID
Explique o mecanismo de Serialização de objetos em Java e a sua finalidade no desenvolvimento de software. Indique como se assinala que uma classe é elegível para serialização e descreva detalhadamente a utilidade e o comportamento do modificador transient e do identificador serialVersionUID. ⚡ 75% Prob.
  • Serialização: O processo de transformar o estado de um objeto na memória (Heap) num fluxo sequencial de bytes para guardar num ficheiro ou enviar pela rede. Requer que a classe implemente a interface marcadora Serializable.
  • O modificador `transient`: Aplicado aos atributos que, por segurança (passwords) ou por falta de necessidade (temporários), não devem ser guardados no fluxo serializado. Esses atributos perdem o seu valor quando o objeto for reconstruído.
  • serialVersionUID: Um ID numérico estático que garante o controlo de versões. Se alterarmos os métodos da classe no futuro, a JVM verifica se o ID guardado no ficheiro bate certo com a versão atual da classe.

17. I/O: Byte Streams vs Character Streams
A biblioteca de Input/Output (I/O) do Java divide-se principalmente em classes orientadas a bytes (Streams) e classes orientadas a caracteres (Readers/Writers). Explique a diferença fundamental entre estas duas famílias de classes, indicando a dimensão dos dados processados e cenários práticos adequados. 🟡 50% Prob.
  • Byte Streams (Classes Stream): Processam dados bit-a-bit à dimensão de 8 bits. Útil para manipulação de dados em bruto/binários, tais como imagens, vídeos, ou ficheiros executáveis. (Ex: FileInputStream).
  • Character Streams (Readers/Writers): Processam texto à dimensão de 16 bits (Unicode). Tratam a conversão de conjuntos de caracteres internacionais, sendo ideais para leitura de ficheiros texto, JSON, XML e relatórios (Ex: FileReader, BufferedReader).

18. Pacotes (Packages) e Modificador Default
Explique o conceito de organização modular por pacotes (package) em Java. 19. Passagem de Argumentos: Primitivos vs Referências de Objetos
Descreva detalhadamente o modo como Java realiza a passagem de argumentos para os métodos, distinguindo o comportamento aplicado a tipos primitivos do comportamento aplicado a referências de objetos. Esclareça os equívocos frequentes associados a este mecanismo. 🔥 95% Prob.
  • Passagem por Valor (Pass-by-Value): Em Java, TUDO é passado por valor.
  • Primitivos: É copiado o valor numérico para a Stack do método. Alterações no parâmetro não afetam a variável original.
  • Referências: É copiado o endereço de memória da referência. Reatribuir o parâmetro local (c = new Container()) não altera a variável original. Contudo, invocar métodos mutadores no objeto (c.setCapacity(50)) altera diretamente o objeto partilhado na Heap!
